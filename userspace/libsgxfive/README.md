# libsgxfive and sgxfive-test

A small C11 library over the **sgxfive** render-node ioctls (`include/uapi/sgxfive_drm.h`), a
test tool that redoes the kernel's debugfs checks from userspace and runs the hardware probes,
and an in-process mock of the kernel side so all of it is tested without the hardware.

This is a development tool. It is not the open-source userspace that upstreaming the UAPI
needs (that is a Mesa driver).

## Layout

| path | what |
|------|------|
| `include/sgxfive.h` | device, DEV_QUERY, BOs, VM contexts, contexts, syncobjs, SUBMIT_JOBS |
| `include/sgxfive_xfer.h` | transfer builders, the program-source interface, the transfer engine |
| `include/sgxfive_render.h` | render jobs: triangle scene builders, CPU reference, render engine |
| `include/sgxfive_tri_probe.h` | probe programs in the triangle's render (`probe --tri`) |
| `include/sgxfive_mock.h` | the mock render node |
| `include/sgxfive_poke.h` | pokes: one word of a built job, by space and index |
| `src/dev.c` | ioctl wrappers and the OS backend (`open`/`ioctl`/`mmap`) |
| `src/xfer.c` | pure builders: DOUTU, PBE state, background objects, texture words, registers |
| `src/xfer_job.c` | the transfer engine: places programs in the client VM, fills and copies |
| `src/prog_asm.c` | the assembled program source: our own programs (default) |
| `src/prog_asm_gen.h` | its tables, generated by `tools/gen_progs.py` (`make gen`); checked in |
| `src/prog_fake.c` | test-double program source (mock only) |
| `src/render.c` | the triangle's programs, MTE state, VDM stream and geometry; the render engine |
| `src/tri_progs_gen.h` | its programs, generated by `tools/gen_tri_progs.py --user`; checked in |
| `src/tri_probe.c` | replaces programs of the triangle's render for `probe --tri` |
| `src/mock.c` | the mock: kernel rules plus small transfer and render interpreters |
| `src/poke.c` | parsing, checking and applying pokes; the target hash |
| `tools/sgxfive-test.c` | the CLI |
| `tools/gen_progs.py` | assembles `asm/transfer/` into `src/prog_asm_gen.h` |
| `tests/` | C tests (TAP), `prog_dump.c` (a driver for `test_prog_asm.py`), pytest tests |
| `third_party/` | Linux's `drm.h`/`drm_mode.h` (MIT) and non-Linux shims; see its README |

`tools/gen_tri_progs.py` lives in the top-level `tools/`: it assembles `asm/tri/` and the
transfer programs the triangle reuses.

## Build and test

```sh
make            # build/libsgxfive.a, build/sgxfive-test
make check      # C unit tests, then pytest on the CLI and the programs, against the mock
make check CC='cc -m32'   # the same on i686 (layout test included)
make gen        # regenerate src/prog_asm_gen.h and src/tri_progs_gen.h after editing asm/
build/sgxfive-test --mock query   # the tool against the mock
```

No dependencies beyond a C11 compiler and, for the pytest tests, Python with pytest (the
repo's `.venv/bin/pytest` if present, else `pytest`; override with `PYTEST=`) and a host
`cc` for `tools/usse-asm`, which `test_prog_asm.py` and `make gen` run. libdrm is not used:
the library calls the ioctls directly with the UAPI header. It builds and passes on macOS,
Linux x86-64 and Linux i686. Running on the hardware is described in the last section.

The C tests are plain programs printing TAP (`tests/tap.h`):

- `test_uapi`: every UAPI struct is the sum of its members (no implicit padding, so i686 and
  x86-64 agree), sizes and offsets, the transfer command at the offsets of the firmware's
  register block, flag masks;
- `test_xfer`: the pure builders against the worked examples of `doc/specs/transfer.md`
  (§4.2, §4.3) and `doc/specs/fw_format.md` (§9.4–§9.6, §10.4): DOUTU words, PBE state,
  background objects, the truncated texture coordinates, T0–T3, the register block, the
  `USSE_LIMM` split;
- `test_dev`: the wrappers against the mock: discovery by driver name, DEV_QUERY size rules
  and the heap table, BO flags and size, VM_MAP heap and overlap rules, contexts, syncobjs
  (binary and timeline), and the SUBMIT_JOBS validation rules: the reserved update list,
  array strides, job and sync-op counts, waits checked for the whole call before anything
  runs, and the per-file limits on VM contexts and contexts;
- `test_job`: fills and copies through the engine, once with each program source: with the
  debugfs-test heap layout (`--mock=harness`) the programs equal the kernel's debugfs fills
  and copies word for word; every destination dword is checked for each rectangle of the
  transfer table; isolation between VMs, faults, lost contexts, read-only maps; the errors
  failed jobs' fences carry (`-EIO` for the job that faulted, `-ECANCELED` for its context's
  jobs behind it, none for another context's) and the waits that report them;
- `test_prog`: the assembled source: its metadata equals the fake's, every word the fake
  writes is the same over random placements, the bodies the fake leaves zero are filled,
  and an unplaced or unreachable `DOUTU` target fails;
- `test_render`: the render builders at the addresses of the kernel's debugfs triangle test
  produce its words (`sgx_tri.c`, which the linux fork gains with the 3D unit), other target
  sizes change exactly the size-dependent words, `sgxfive_tiling()` follows the tiling rule
  of the UAPI header field by field, and the CPU reference and the pixel checker;
- `test_render_job`: render contexts and jobs against the mock: DEV_QUERY, the kernel's
  rules on contexts, commands and the reserved render heaps, the triangle at several sizes
  every pixel checked, contexts that state their largest target (bounds, targets within it
  rendered, larger ones refused), a faulting render losing its context and its wait
  reporting `-EIO`, a scene overflowing the parameter buffer failing with `-ENOSPC` at the
  PB sizes and targets where the hardware overflows (its context kept), transfers keeping
  `PDS_EXEC_BASE` at the PDS heap base, transfers and renders interleaved;
- `test_tri_probe`: replacing each program slot of the triangle's render, the words the
  host patches in a replacement, the vertex copies, extra vertex outputs and state-block
  edits of `probe --tri`;
- `test_poke`: pokes: parsing, the checks against a job's views (a space the job lacks, an
  index past a view), set and flip, the views of fills, copies and triangles (their sizes
  are the built job's), and on the mock that a poke of the first and last word of every
  view changes exactly that word of the submitted job and nothing else.

`tests/test_cli.py` drives `sgxfive-test --mock` through every subcommand, and
`tests/test_cli_poke.py` the job options below. `tests/test_prog_asm.py` checks that
`src/prog_asm_gen.h` is what `gen_progs.py` writes, and runs `build/prog_dump` against
`tools/fwcutter/fwload.py`'s `build_tq()`: the debugfs placements and 100 random placements
and parameter sets on a firmware built from our source alone, and, with the user's
`libsrv_init.so` and `libsrv_um.so`, 50 more on the file fwcutter cuts from them. Every byte
must match.

## The mock

`sgxfive_mock_create()` returns an object whose `struct sgxfive_backend` replaces `open`,
`close`, `ioctl`, `mmap` and `munmap`; every library function takes a backend
(`sgxfive_dev_open(be, ...)`, NULL meaning the real one), so the code under test is the code
that runs on the hardware. The mock implements the kernel's rules as the UAPI header states
them:

- render nodes: optionally another driver on `renderD128` (discovery must skip it);
- DEV_QUERY with the size rules of the PowerVR Rogue UAPI (`pvr_drm.h`), and the kernel's
  heap table of the `REV1` layout (default; quirk `SAMPLE_CACHE`, bridge revision 3) or the
  heap layout of the kernel's debugfs tests (`--mock=harness`); `render_pb_pages` from the
  configuration (`--mock-pb-pages=N`, 0x23 to 0x422, the default 0x422), as the kernel's
  debugfs `render_pb_pages` sets it for new render contexts;
- GEM BOs of at most 1 GiB (the mock's own memory stops at 65 MiB, `-ENOMEM` beyond), with
  mmap only when `ALLOW_CPU_ACCESS`; zeroed padding and flag masks everywhere;
- VM contexts with per-mapping read-only flags, mappings only inside one user heap, `-EEXIST`
  on overlap, whole-mapping unmap; BOs live while mapped; closing the file frees everything;
- transfer and render contexts (a render context states its largest target, 1 to 4096 each
  way, a transfer context none; 32 render contexts per VM; none in the debugfs-test layout,
  which has no room for the reserved render heaps); at most 32 VM contexts and 64 contexts
  per open file (`-ENOSPC` beyond);
- DRM syncobjs (`CREATE`, `DESTROY`, `WAIT`, `TIMELINE_WAIT`, and `HANDLE_TO_FD` with
  `EXPORT_SYNC_FILE`, whose sync_file answers `SYNC_IOC_FILE_INFO` with the fence's status);
- SUBMIT_JOBS: 1 to 16 jobs of up to 16 sync ops, arrays at a stride of 1 to 256 bytes (a
  shorter element zero-extended, a longer one with a zero tail), all jobs validated before
  any runs, the failing index in `jobs.count`, the header's checks (job and context types
  match, the addresses the pixel pipe fetches from in user heaps, `PDS_EXEC_BASE` of
  transfers at the PDS heap base, render targets within their context's maximum with the
  tiling words of their size), the update list rejected while `max_updates` is 0, and waits
  needing a fence (as `drm_syncobj_find_fence`) unless an earlier job of the same call
  signals the same handle as the same type.

Jobs run synchronously.

**Transfers.** An interpreter follows the job's own pointers through its VM: pixel-event PDS
→ EOT program → PBE state; background object → PDS primary → shader (fill colour) or
texture words (copy); the vertices and the render box clip the rectangle. So a wrong
address, encoding or placement shows as wrong pixels or a fault (a mutation of any builder
fails `test_job`).

**Renders.** The same, for the scenes our builders make: the VDM stream's state blocks (the
pixel primary's fill colour, the viewport) and triangle index lists through their vertex PDS
program, the background object's colour, and the PBE state of the end-of-tile program; each
pixel of the target gets the last triangle covering its centre, or the background.

**Faults.** A fault writes nothing, counts in the stats and loses the context, as with the
kernel's recovery: the job's fence signals with `-EIO`, later jobs of the context in the same
call with `-ECANCELED`, and later submissions get `-ECANCELED`. A read of GPU memory that
runs past the end of a mapping faults.

**Unknown shaders.** A fill shader whose colour instruction is not a limm `mov` is a program
the interpreter does not know, which it treats as a hang (a fault). For `probe`, the mock
takes the colour from the program's second instruction, as for fills, and treats any other
second instruction as a hang; with `--coords` it runs only the copy shader itself
(`mov.skipinv.end o0, pa0`).

**Parameter-buffer overflow.** A render whose scene would overflow its context's parameter
buffer writes nothing and signals `-ENOSPC`, keeping its context, as the kernel does. A scene
needs two pages plus one per 128 tiles of the target; it overflows when that exceeds the
parameter buffer's `pages - 0x22` pages (the pages left after the buffer's own descriptor).
This reproduces where the hardware overflows, not the hardware's accounting.

What the mock cannot tell: whether the real firmware and hardware accept the programs and
registers. That is what the hardware runs are for.

## Library API in brief

```c
sgxfive_dev_open(be, path_or_NULL, &dev);       /* scans renderD128..191 for "sgxfive" */
sgxfive_dev_info(dev);                          /* GPU, FW, job limits, runtime, heaps */
sgxfive_bo_create(dev, size, flags, &bo); sgxfive_bo_mmap(bo, &p); sgxfive_bo_destroy(bo);
sgxfive_vm_create(dev, &vm); sgxfive_vm_alloc(vm, heap, size, align, &addr);
sgxfive_vm_map(vm, addr, bo, offset, size, flags); sgxfive_vm_unmap(vm, addr, size);
sgxfive_ctx_create(vm, &ctx); sgxfive_ctx_destroy(dev, ctx);  /* a transfer context */
sgxfive_render_ctx_create(vm, max_width, max_height, &ctx); /* targets up to that size */
sgxfive_syncobj_create(dev, signaled, &h); sgxfive_syncobj_wait(dev, h, point, timeout_ns);
sgxfive_syncobj_wait_job(dev, h, point, timeout_ns, &job_error);
sgxfive_syncobj_fence_status(dev, h, &status);  /* 1, 0, or the fence's error */
sgxfive_submit(dev, jobs, n, &failed); sgxfive_submit_transfer(dev, ctx, flags, cmd, w, s);

sgxfive_xfer_create(vm, ctx, program_source, &x);
sgxfive_xfer_fill(x, &dst, &rect, colour, signal);
sgxfive_xfer_copy(x, &src, sx, sy, &dst, &rect, signal);
sgxfive_xfer_wait(x, timeout_ns);

sgxfive_tri_default(&params, width, height);   /* the first triangle at that size */
sgxfive_render_create(vm, render_ctx, &r);
sgxfive_render_tri(r, &params, signal);
sgxfive_render_wait(r, timeout_ns);
sgxfive_tri_check(&params, sgxfive_render_fb(r), &counts);  /* against the CPU reference */
sgxfive_render_destroy(r);
```

Functions return 0 or a negative errno. The VM address allocator never reuses a range: an
engine created and destroyed many times in one VM eventually exhausts its heap.

### Job errors

A job that faults or hangs is recovered by the kernel and fails: its fence signals with an
error (`-EIO` for a fault, `-ETIMEDOUT` for a hang without one, `-ECANCELED` for jobs of the
lost context queued behind it). A syncobj wait still returns 0 for such a job, so the waits
read the fence's status from a sync_file exported from the syncobj (`SYNC_IOC_FILE_INFO`)
and return that error: `sgxfive_syncobj_wait()` for a binary syncobj, `sgxfive_xfer_wait()`
and `sgxfive_render_wait()` for the engine's last job. `sgxfive_syncobj_wait_job()` returns
the wait's result and the job's error apart. A signalled timeline point carries no error
(the kernel's chain fences drop it), so waits on points report only the wait.

### Program sources

The kernel builds no GPU programs: userspace places them in its own VM. The transfer engine
takes them from a `struct sgxfive_prog_source`, two callbacks over the ids, metadata and
parameters of the firmware file's transfer-queue templates (`doc/specs/fw_format.md` §9,
§10):

- `meta(id)` → heap, temporaries, attributes, size, alignment, PDS data size;
- `build(id, env)` → the finished image, given the parameters (colour, PBE words, texture
  words) and where everything was placed (addresses and DOUTU words of the USE programs).

The engine places the seven programs of a fill or copy in a private three-page BO mapped into
the context's VM (PDS_PIXEL, USSE_PIXEL and GENERAL pages, 16-byte slots, the placement of
the kernel's debugfs fills and copies), computes the DOUTU words, builds the background
object and the register block, and submits. One job is in flight per engine.

Two sources exist:

- `sgxfive_prog_asm_create()`, the default: our own programs from `asm/transfer/`. They
  assemble bit for bit to the templates fwcutter cuts from `libsrv_um.so`, so their images
  run on hardware, and the library needs no file. `build` is `fwload.build_tq()` for one
  program: copy the template, apply its `TQ_PATCHES` records in order (format §9.4).
- `sgxfive_prog_fake_create()`, a test double that writes the words the specifications
  give and leaves the template bodies it does not model (USE secondary, pixel-event PDS
  code) zero. Its images must never reach a GPU: the CLI refuses `--programs=fake` without
  `--mock`.

The assembled programs are generated into C, not assembled at build time. `src/prog_asm_gen.h`
holds the words, each commented with its instruction, and the `TQ_META` and `TQ_PATCHES`
records of `tools/fwcutter/facts.py`; it is checked in and `test_prog_asm.py` fails when it
is stale. That keeps the library a plain C11 build: cross and `-m32` builds need no host
assembler, Python or build-time tool, and the generated words are reviewable in a diff.
These are our programs, so the tables may live in the tree.

The render engine has one source only: the triangle's programs of `asm/tri/` and the fill,
secondary, pixel-event and end-of-tile programs of `asm/transfer/`, generated into
`src/tri_progs_gen.h` by `tools/gen_tri_progs.py --user` (`make gen` runs it;
`tools/test_gen_tri_progs.py` fails when it is stale). `src/render.c` places and patches
them. There is no test double for them: the mock's render interpreter runs these programs.

## sgxfive-test

```
sgxfive-test [--mock[=rev1|harness|none]] [--mock-pb-pages=N] [--device PATH]
             [--programs=asm|fake] <command> [options]

query                          GPU, firmware, job limits and heaps
dummy [-n N] [--kpoke-job N:SPEC]... [--wait-ms MS]
                               N dummy transfers chained through one syncobj

      [JOB OPTIONS]

      [--every-value | --ramp CH=START [--ramp-base V]] [--print-addrs] [--page-before]
      [JOB OPTIONS]
isolation                      kernel-heap-unmappable, same-address-separate-vms,
                               other-vm-address-faults, fault-recovered-quickly,

    [--scratch N [--scratch-fill V] [--scratch-at ADDR] [--scratch-file FILE]]
    [--kpoke-render N:SPEC]... [--kreg-render N:OFFSET=VALUE]...
    [--move N:DX,DY]...
    [--geometry N]... [--keep-going] [--keep-overflow] [--dump-render DIR [--dump-each]]
    [--words DIR] [--wait-ms MS]
    [--depth [--depth-ctl V] [--depth-ctl-next V] [--depth-fill V] [--depth-base V]
           [--depth-pages N] [--depth-dump DIR]]
    [--ctx2 [--share-pb] [--overlap] [--close-first] [--close-first-early] [--words-between]
          [--close-trace] [--wait-second] [--kpoke-render2 N:SPEC]...
          [--kreg-render2 N:OFFSET=VALUE]...]
    [JOB OPTIONS]
contexts [--width W --height H -n N]
regaccess
probe [--stamp] [--temps N] [--coords] [--pixels] [--scratch-pages N] [--pds N --use USE]
      [--place OFFSET=FILE --place-form cbase|exe18] [--scratch-heap texture]
      [--poke xfer:N=V]... [--low ADDR] [--late R:K=V] FILE...
probe --tri SLOT[:N] [--slot SLOT=FILE[:N]]... [--width W --height H]
      [--max-width W --max-height H] [--vertices N [--copy-depth]] [--vtx-coords N]
      [--isp2 V] [--blk-add BIT=V[,V]]... [--blk N=V]... [--cmd N=V]... [--vdm N=V]...
      [--pbe N=V]... [--sideband V] [--temps N] [--pixels] [--dump-render DIR] [--kpoke SPEC]...
      [--obj2 FIRST [--obj2-blk N=V]... [--obj2-pixel FILE] [--obj2-pixpds FILE:N]] FILE...
```

`copy --every-value` uses a source with every value of every channel in each run of 256
pixels, a permutation per channel. `copy --ramp CH=START` makes one channel (a, r, g or b) of
the source count from START, one a pixel (modulo 256), the others `--ramp-base V` (default 0).
`--print-addrs` prints where the source's and destination's buffers lie, and `--page-before`
gives the source's buffer a page before the source, dword i holding `0xB0000000 | i`, so that
a read below the source shows which dword it took.

`tri` renders the first triangle on a render context N times in alternating colours, every
pixel against the CPU reference and the area after the target against a sentinel. The
context takes targets up to `--max-width` x `--max-height` (default: the target's size).
`--fault` unmaps the scene's VDM stream page first, so the render faults and fails.
`--scratch N` maps N more pages (their address printed) for a kernel poke to point a unit
at, filled with V (default 0.25f) before each render; the dwords that changed are reported
page by page. `--scratch-at ADDR` maps them at ADDR (a heap's page, say, that a unit fetches
from) instead of in the general heap. `--kpoke-render N:SPEC` writes SPEC to the kernel's
debugfs `kpoke` just before render N. `--move N:DX,DY` draws render N's triangle DX, DY pixels
away. `--geometry N`
submits render N as geometry only (the scene left open for the next render, nothing drawn).
`--keep-going` reports every render, checked or not. `--dump-render DIR` copies the kernel's
debugfs `render_param` and `render_tadata` to `DIR/tri.param.bin` and `DIR/tri.tadata.bin`
after the renders. `--words DIR` copies the kernel's debugfs `render_words` (the render
context's words, a kpoke line each) and `buf09` (the TA/3D control block) to `DIR/words.N.txt`
and `DIR/ta3d.N.bin` before the first render (N = 0) and after each render N, failed or not,
while the context lives (`tools/usse-asm/render_words.py` reads them); with `--regs LO-HI` each
snapshot is followed by `tri: registers at snapshot N` and the register range.
`--wait-ms MS` waits MS milliseconds for each render (default 5000), so a script can read the
kernel's state while a held hang lasts.
`--keep-overflow` counts a render whose scene overflowed the parameter buffer (the job's
`-ENOSPC`, its context kept) instead of failing the run: the line `tri WxH #N: overflowed, ...`
gives the target's colours as the other lines do, the run goes on, and the closing line reads
`tri: K of N renders ok, M overflowed`; any other failure still stops it. `--dump-each` (with
`--dump-render DIR`) copies the kernel's `render_param` and `render_tadata` after every render N
as `DIR/tri.N.param.bin` and `DIR/tri.N.tadata.bin`, an overflowed render's included (its state
page holds what a partial render stored), besides the last render's `DIR/tri.*.bin`.
`--depth` maps a depth buffer of the target's width x height dwords and sixteen pages over
(`--depth-pages N` sets the size), fills it with `--depth-fill V` (default 1.0f) and arms, before
every render, the kernel pokes `ta:7^=0x80` (the render flags' depth-buffer bit), `rd:1` (the ZLS
base, `--depth-base V`, default 0x3e000000, the general heap's), `rd:11` (the ZLS control,
`--depth-ctl V`, default 0x0017100c) and `rd:12`, `rd:13` (the load and store bases, as offsets
from the ZLS base) at the buffer. `--depth-ctl-next V`
is the control of renders 2 on, and the buffer is then filled before render 1 only, so a later
render loads what the earlier one stored. After each render `depth #N` gives the dwords that
differ from the fill, the number of distinct values and the four most frequent; `--depth-dump DIR`
writes the buffer as `DIR/depth.N.bin`. The triangle's depth test is the job option `--poke
blk:1=0x00400200` (test less). `--depth` does not take `--ctx2`.
`--ctx2` creates a second render context in the VM, for the same size of target, and renders the
same scene on it after each render of the first, in the other pair of colours, checking it on
its own (lines `tri2 ...`); the contexts' buffers are destroyed second context first.
`--share-pb` writes `Y` to the kernel's debugfs `render_share_pb` before the second context is
created, so that it runs on the first's parameter buffer (the linux fork's debug option).
`--overlap` submits the second context's job before the first's is waited for; whether both were in
the firmware at once is not checked. `--kpoke-render2 N:SPEC` is `--kpoke-render` for the second
context's render N (with `--overlap`, written 30 ms after the first context's job is submitted, so
that the kernel's kick of the first has taken what was armed before it).
`--close-first` closes the first context (the donor of a shared parameter buffer) before the
second; `--close-trace` prints, after each close and 500 ms after both, the lines of the
kernel's debugfs `render_cleanup` and dwords 32, 46 and 47 of `buf09`, and `--wait-second`
(with `--overlap`) waits for the second context's job before the first's, so that a first job
that never ends does not hide whether the second ran. `--scratch-file FILE` fills the first
dwords of the `--scratch` pages from FILE (a table the host built) before each render and
counts the dwords the render changed against that content.

`--kreg-render N:OFFSET=VALUE` (or `OFFSET^=VALUE`) writes a register to the kernel's debugfs
`kregnow` just before render N, `--kreg-render2` before the second context's render N, so that a
register the host does not usually write (register 0x0740 is one) holds a chosen value at that kick.
`--close-first-early` closes the first context in the last iteration, after its render and before
the second context's: the kernel's cleanup of the first runs, `--words DIR` saves a snapshot
`words.(100 + N)` and `ta3d.(100 + N).bin` before the close and `words.(200 + N)` and
`ta3d.(200 + N).bin` after it, and `--close-trace` prints the cleanup's trace.
`--words-between` (with `--words`) saves the same snapshot `(100 + N)` before every second-context
render, with the first context open.
`dummy --kpoke-job N:SPEC` and `fill --kpoke-job 1:SPEC` write a kernel poke (`th:W=V`, a word of
the transfer context's HW context, is applied to that submission) just before job N;
`dummy --wait-ms MS` sets how long the chain is waited for, and a job that does not complete is
reported as such.

`probe --stamp` prints each finished job's start and end in CLOCK_REALTIME ns (`job window`),
to place a write from another process (a debugfs `kregnow` write, say) inside the job.

`contexts` creates N render contexts (default 32) for targets up to W x H (default 64 x 64)
in one VM, and prints the memory they take: MemFree and LowFree of `/proc/meminfo`, before
and after.

`regaccess` is the register-access probe: client fill shaders that read and write SGX
registers with the instructions the firmware uses for MMIO, read temporaries they did not
write, and kick code base 15. It prints what reached memory, with no pass or fail. It means
something only on the hardware: the mock's interpreter knows no `ldr`/`str`, so its probes
fail there as hangs.

### Probes

`probe` runs one-program hardware probes, assembled by `tools/usse-asm`: a probe presets its
inputs, runs the instruction under test and writes the result to `o0`.

Each FILE runs as the shader of its own 64x32 fill with N temporaries (`--temps`, default
32, at most 128). The command prints `o0` (`o0 0x... (2048 of 2048)`, or `mixed` with the
four most frequent values) or `failed: ...`, and the dwords of a 64 KiB scratch buffer the
program changed. A `mov d, #0x5CAFnnnn` (a limm) is patched to load the scratch buffer's
address + `nnnn`; the buffer starts with dword `i` = `0xD0000000 | i`, so loads see which
dword they read and stores show up as changed dwords. A failed probe still prints the dwords
changed before the job hung or faulted, or `scratch unchanged`.

- `--coords` runs FILE as the shader of a 64x32 copy whose source texel (x, y) is
  `(y << 16) | x`, so that `pa0` holds the pixel's coordinates.
- `--pixels` also prints every pixel, a row a line (`row Y: v0 ... v63`).
- `--pds N --use USE`: each FILE is a PDS program (pds-asm, N data dwords) run as the
  fill's PDS secondary, its U0-U2 set to kick the secondary task, with 16 secondary
  attributes for its `douta` results; USE, the fill's shader, reads and stores them.
- `--poke xfer:N=V` sets a word of the fill's transfer command (the job options below).
- `--low ADDR` maps the scratch buffer again at ADDR, a page in the first MiB (page 0
  excepted), for a PDS program's loads and stores; it needs the kernel's debugfs `vm_low`.
- `--scratch-pages N` (16 to 64) sizes the scratch buffer (default 16 pages, 64 KiB); the
  immediates 0x5CAFnnnn still reach 64 KiB. `--low` and `--late` are checked against the size
  whatever their order on the command line (the low mapping and the scratch buffer must end
  within 1 MiB).
- `--scratch-heap texture` puts the scratch buffer in the texture heap, so that a texture in
  it is in the texture region (its address 0xf0000000 and up).
- `--place OFFSET=FILE --place-form cbase|exe18` maps the USE program FILE at the USSE pixel
  heap's base + OFFSET (a multiple of 8, below the heap's 5 MiB), patches its scratch
  immediates, and starts it in place of the fill shader (the probe's own program, at the
  heap's base, stays unstarted) by a primary DOUTU whose EXE and CBASE hold the offset as
  `cbase` (bits 18:3 in EXE, bits 22:19 in CBASE) or as `exe18` (bits 20:3 in an 18-bit EXE,
  CBASE 0).
- `--late R:K=V`: while the job runs, once scratch dword R leaves its fill (or after
  200 ms), the host writes V to dword K.

`probe --tri` runs each FILE as the program SLOT of the first triangle's W x H render
(default 64 x 64), on a render context for up to `--max-width` x `--max-height` (default
W x H). The slots are `pixev`, `eot`, `vtxpds`, `vtxuse`, `pixel`, `pixtask`, `pixpds`,
`state`, `bgpds` and `bgpixel` (the background object's primary PDS program and pixel shader);
a PDS slot takes N data dwords. The new programs are patched as the defaults
(`include/sgxfive_tri_probe.h`), with the scratch buffer; the command prints `tri WxH, SLOT
... replaced`, the target as `o0` and every scratch dword changed.

- `--slot SLOT=FILE[:N]` replaces another slot's program in every render.
- `--vertices N` (3 to 1500, whole triangles) draws copies of the triangle after it, each
  1/16 pixel on, so that the vertex programs run for more vertices than one task's (more
  than 126 move the vertices and indices to the rig's extra gen pages);
  `--copy-depth` puts copy c at clip z = c / 16.
- `--vtx-coords N` (1 to 11) adds N output dwords per vertex, coordinate sets of four and
  the rest (OUTSEL, coordsize).
- `--isp2 V` puts ISP word 2 (stencil) V in the state block, in place of the wrap word.
- `--blk-add BIT=V[,V]` adds presence bit BIT (2-5, or 7 with two words) and its words to
  the state block, which grows.
- `--blk N=V`, `--cmd N=V` and `--vdm N=V` set word N of the state block, the render
  command and the VDM stream (after `--vtx-coords`); `N^=V` flips the bits of V. With
  `--obj2` the VDM stream is the two-object one, words 0 to 18 (word 9 the second state
  block's), changed after the second object is built.
- `--pbe N=V` (N 0 to 3) sets word N of the end-of-tile task's PBE words (the default's or
  the `eot` slot's; word 4 is `--sideband`).
- `--sideband V` (with an `eot` slot) sets the end-of-tile `emitpix2`'s sideband (default
  0x200).
- `--dump-render DIR` copies the kernel's debugfs `render_param` and `render_tadata` to
  `DIR/NAME.param.bin` and `DIR/NAME.tadata.bin` after the render.
- `--kpoke SPEC` is written to the kernel's debugfs `kpoke` before each case's render.
- `--obj2 FIRST` (with `--vertices`) makes the copies from vertex FIRST on a second object,
  its state block the first's with the `--obj2-blk N=V` words set and its pixel shader
  `--obj2-pixel FILE` (or the default fill) and its primary pixel PDS program
  `--obj2-pixpds FILE:N` (N data dwords; or the default's), which may `douta` the pixel
  side's constants.
- A replacement program's `mov d, #0x5CB0nnnn` (limm) or PDS data dword 0x5CB0nnnn loads
  the render target's address + nnnn, as 0x5CAFnnnn does the scratch buffer's: a pixel
  program can read the target it renders to.

### Job options: pokes, pixels and registers

`fill`, `copy` and `tri` take the options a sweep needs (a sweep runs one job many times
with one word changed each time):

```
--poke SPACE:INDEX=VALUE      set one word of the built job, right before it is submitted
--poke SPACE:INDEX^=VALUE     flip the bits of VALUE in it (relative to what the job wrote)
--pixels                      every pixel of the target, "row Y: v0 v1 ..."
--regs LO-HI                  the SGX registers LO to HI (byte offsets, dword-aligned, below
                              0x4000) after the job, read-only through /dev/mem; needs root
```

A poke addresses a word by space and index, never by name, so a sweep needs no name for
what it changes (`include/sgxfive_poke.h`). `--poke` repeats, up to 64; the pokes apply in
order to every job of the command. The spaces, and their sizes in the jobs we build:

| space | fill | copy | tri | the words |
|-------|------|------|-----|-----------|
| `cmd:N` | | | 26 | `struct drm_sgxfive_render_cmd`, dword N |
| `xfer:N` | 42 | 42 | | `struct drm_sgxfive_transfer_cmd`, dword N |
| `vdm:N` | | | 11 | the triangle's VDM stream |
| `eos:N` | | | 2 | the end-of-scene state block |
| `blk:N` | | | 18 | the triangle's state block |
| `pds:SLOT:N` | 4/4/20 | 12/4/20 | see below | the data dwords of the PDS program in SLOT |
| `tex:N` | | 4 | | texture word TN, in the copy primary's data (T0-T3 at 8, 9, 6, 7) |
| `bg:N` | 17 | 23 | | the background object |

The PDS slots: `prim`, `sec` and `pixev` for fills and copies (the primary, the secondary
and the pixel-event program); for `tri`, `vtx` (8), `state` (8, the triangle's state),
`eos` (8, the end of scene's), `prim` (4), `bgprim` (4), `sec` (4) and `pixev` (20). A space
the command's job does not have, a slot it does not have or an index past the end is a usage
error (exit 2) before anything runs.

The engines know nothing of pokes: `sgxfive_xfer_set_hook()` and `sgxfive_render_set_hook()`
take a function that the engine calls with the views of each built job right before
submitting it, and `sgxfive_poke_hook` is the one that applies pokes; an error from it fails
the job unsubmitted.

The three commands print, for each job, the lines a sweep reads:

```
job: ok | job: rejected (ERROR) | job: failed: job faulted, context lost (...)
target: WxH hash 0x0123456789abcdef
diff: N of W*H pixels[, first (X, Y) 0xVALUE expected 0xVALUE]
outside: N dwords
```

`rejected` is a submission the library or the kernel refused, nothing ran; `failed` is the
job's error as the wait returns it (fault, hang, parameter-buffer overflow). The hash is the
64-bit FNV-1a of the target's pixels, row after row (the fill or copy rectangle, the render
target). The difference is against the CPU reference (the fill colour, the copied pattern,
the triangle with either colour accepted near its edges); `outside` counts the dwords of
the destination buffer outside the target that are not the sentinel (for `tri` the area
after the target). These lines come after the job also when it failed, since a faulting job
may have written pixels. With pokes, `tri` does not draw the target as text when it is
wrong; `--pixels` prints it.

`--regs` prints `reg 0xOFFS 0xVALUE` lines after the job, read from the register bank at
physical 0x80080000 (the laptop's; `SGXFIVE_REGS_BASE` overrides it) without writing
anything; reading needs root. The mock prints `regs: not available on the mock`.

### Results and exit status

A job that faults or hangs is reported with its error and the lost context, as the wait
returns it: `probe NAME: failed: job faulted, context lost (Input/output error)` (`job hung`
for `-ETIMEDOUT`, `job cancelled` for `-ECANCELED`); `regaccess` prints
`NAME: job failed: ...` and `tri` exits 1 with
`sgxfive-test: render: job faulted, context lost (...)`. A render whose scene overflowed the
parameter buffer keeps its context: `tri` exits 1 with
`sgxfive-test: render: scene overflowed the parameter buffer, context kept (No space left on
device)`; debugfs `sgx/render_pb_pages` shrinks the PB on the hardware, `--mock-pb-pages` in
the mock. A probe whose job completes without writing a pixel prints
`failed: no pixel written`. `isolation` checks that each faulting fill's wait returns `-EIO`
and the re-run innocent job's returns 0.

Exit status 0 when every check passes, 1 on a failed check or call, 2 on usage errors.
`fill`, `copy`, `isolation` and `regaccess` print the program source in their first line
(`programs asm` or `programs fake`). Each check command redoes a debugfs file of the
kernel's (`dri/N/sgx/`):

| command | debugfs |
|---------|---------|
| `dummy` | `xfer_dummy`, `xfer_sync` |
| `fill` | `xfer_fill` (sentinel-filled destination plus a guard page, every dword checked) |
| `copy` | `xfer_copy` (a source in which every byte varies) |
| `isolation` | `xfer_iso`, `alias_ro`, `xfer_ro` |
| `tri` | the triangle test, `sgx_tri.c`, which the linux fork gains with the 3D unit |

## On the hardware

The same binary runs on the laptop without `--mock`, against the linux fork's render node:
`query`, `dummy`, `fill`/`copy`/`isolation`/`regaccess` with the assembled programs, and
`tri` with the triangle's.

1. The kernel: the linux fork with gma500 and its sgxfive part, loaded with
   `gma500_gfx.sgx_render=1` on the kernel command line; without it the device has no render
   node. `probe`, `regaccess`, `--kpoke*`, `--dump-render`, `--low` and the PB and timer
   knobs need the debugfs group of a kernel built with `CONFIG_DRM_GMA500_SGXFIVE_DEBUG`.
2. The firmware: `/lib/firmware/sgx545_ukernel.fw`, the file `tools/fwcutter` writes
   (`doc/specs/fw_format.md`); the kernel loads it when it boots the firmware.
3. The tool: `tools/bringup/push-tools.sh` builds it for i686 in the `resgx545/arch32:igt`
   image on the build host and copies it to the laptop's home directory; the hosts come from
   `tools/bringup/local.env` (see `local.env.example`).
4. `--regs` reads `/dev/mem`: run it as root.
