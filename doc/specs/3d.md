# SGX545 3D: the TA and 3D paths of the EDM, and the state a render runs on

A render on SGX545 is two jobs of the tile-based deferred renderer (tbdr_primer.md §3): the tile
accelerator (TA) walks a vertex data master (VDM) stream and bins the scene into the parameter
buffer (PB), and the 3D pipe renders it tile by tile. Both are started by the microkernel (the EDM)
from a TA command the host writes into a render context's queue. This document gives what the EDM
does with that command, the structures it reads, the registers it loads, and what the state words
of a render do on the hardware.

Sources, as everywhere in resgx545: our disassembly of the firmware, for interoperability (RE:
facts only, no code), and runs on the laptop through the linux fork (HW). Each section ends with
its evidence; an inference is marked [infer], and an open point names its question. How a client
submits a render through the render node, and the scene rules seen there, are render_uapi.md §8.4
and §8.5; the transfer path, which shares the EDM's queues and completion, is transfer.md §3.

Conventions. Instruction numbers are the microkernel's indices in hex (byte offset / 8). Dwords
of a structure are numbered from 0. `TA3DCtl` dword *k* is dword *k* of the EDM's TA/3D control
block (glossary `ta3d_ctl`); `sa8` and `sa9` are the EDM's TA and 3D state words, secondary
attributes the firmware keeps. Registers are named as in the glossary and given by offset where
no name is settled. "TA flags" is the TA command's dword 1 (`GEOM_FLAGS`), "render flags" its
dword 7 (`FRAG_FLAGS`), which the TA kick copies into the render details. A tile is always given
with its size: a 32 x 16 tile is the TA's region, the unit of `CR_TE_SCREEN` and of a PBE emit; a
16 x 16 tile is half of one, the unit of `CSTREAM.PRIM_TILES` and of the pixel-event program's
`ir0`.

## 1. Objects

A render involves these structures. The EDM reads them through its own directory list, except
where a section says it switches to the context's (§4.3, §5.2, §5.3, §6.1).

### 1.1 The render context

| dword | content |
|---|---|
| 0 | flags: bit 4 `CONTEXT_FLAGS.SUSPEND` (skipped), bit 5 (§6.3), the new-context flag (§4.3) |
| 1 | priority: the queue index the context waits on |
| 3 | the TA client CCB's base |
| 4 | the address of the CCB control block `{write offset, read offset}`, offsets in bytes |
| 5 | `submitted_commands`: TA commands queued and not finished |
| 6 | the PB descriptor (§1.5) |
| 8, 9 | the pending-render list, head and tail |
| 10, 11 | the ready-render list, head and tail |
| 12, 13 | links of the TA queue |
| 14, 15 | links of the 3D queue |
| 16 | a process id the EDM records |

The EDM owns dwords 5 and 8 to 15. Evidence: E156, E157, E159, E161, E163, E165, E167.

### 1.2 The TA command

The command sits in the context's TA client CCB at the read offset (§4.2). The dwords the EDM
reads:

| dword | content |
|---|---|
| 0 | size in bytes: the read offset advances by it, modulo 64 KiB |
| 1 | TA flags (§4.6) |
| 2 to 4 | `cmd_ta.pds_bgnd`: the background object's first three words (§5.3) |
| 5 | `cmd_ta.num_vertex_partitions`, placed as bits 31:27 of `CR_DMS_CTRL` |
| 7 | render flags (§4.6) |
| 8 | frame number |
| 9 | the PB descriptor the TA finish updates |
| 10 to 13 | a PB threshold update: TA, ZLS, global and PDS thresholds |
| 14 | the render details (§1.3) |
| 15 | the destination sync list |
| 16 | our kernel's RT data set; moved by `0x8` or `0xc` it changes nothing (E304, one run) |
| 17 | the RT data (§1.4) |
| 18 to 20 | copied to render details dwords 72, 70 and 71 |
| 21 | `cmd_ta.num_patches_3d`: the count of `{address, value}` pairs from dword 170 |
| 22 | `cmd_ta.shared` control flags: bit 0 is READY |
| 23, 24 | counts of the TA status pairs (from dword 70) and the 3D status pairs (from dword 134) |
| 25 to 28 | the TA transfer-queue sync: write pending, its address, read pending, its address |
| 29 to 32 | the 3D transfer-queue sync, the same four words |
| 33, 34 on | the source sync count and the source syncs, four dwords each |
| 68, 69 | the TA to 3D dependency: pending value and write-complete address |
| 142 to 169 | the TA register words (§4.3) |
| 170 on | the patch pairs |

The patch pairs are memory writes, `*address = value`, applied when the TA kick copies the command
(§4.4): a way to change the render details per kick, not register writes. Dwords 2 to 4 are the
background object's PDS words as the host gives them: a render command whose first word has a
high bit wrong faults after part of the first 32 x 16 tile (E301).

Evidence: E156, E158, E159, E161, E301, E304.

| 65, 66 | the render-target count and the next render-target index |
| 67, 68 | `rt_patch_dev_vaddr` and its list, two dwords per render-target index (§5.2) |
| 69 | `pds_bgnd_list_dev_vaddr`: one background-object word per render-target index (§5.3) |
| 70, 71 | the Z and stencil buffer strides per render-target index |
| 73 | `te_context_state`: the tiling engine state saved between kicks of a scene |
| 74, 75 | links of the context's pending and ready lists |
| 76 to 78 | `pds_bgnd`, copied from the command |

| 80 | frame number |
| 81, 82 on | the 3D status pairs |
| 90, 91 on | the source syncs |

Dword 9 loads `CR_REG_0148`, which keeps bit 0 only; no value of the dword changes the triangle,
five copies, a fill or a copy of a shader that writes `o0` only (E302, one run; E412, three runs;

Evidence: E158, E162, E163, E164, E165, E302, E304, E406, E412; Q043.

### 1.4 The RT data and the RT data set

An RT data holds one scene's tiling state:

| dword | content |
|---|---|
| 1 | the render details in flight: set by the TA kick, cleared at the render's end |
| 2 | an offset the partial render's region base is derived from (§6.4) |
| 4 | `bgobj_dev_vaddr`: the background object (§5.3) |
| 5, 6, 7 | the DPM state, the DPM control and the OTPM areas |
| 10 | the number of render targets |
| 11 | the region-header stride per render-target index |
| 12 | the RT status words, one per render target |
| 13 | `state`: bit 4 free, bit 5 scene ended, bit 6 aborted, bit 7 out of memory |

The RT data set counts per scene: dword 0 `pending_count_dev_vaddr` (the address of the host's
pending count), dword 1 `executed_count` (incremented per kick that does not end the scene and
per completed render with render flag `0x400`), dword 3 `num_out_of_mem_signals`, dword 4
`num_spm_renders`. A host gives the RT data `state` bit 4 before a first kick: the TA pick waits
for it (§4.2).

On the hardware render details dword 54, not TA command dword 16, points at the set the firmware
counts in, and the count lands one dword past the address it holds: moved by `0xc` it makes our
kernel report a parameter buffer overflow after a render and after a geometry kick (E304, one
run), and moved by `0x8` the count of a render and of a geometry kick are read in dword 3 (E315,
one run).

Read while the context lives, `executed_count` rises by one at every kick, the geometry kicks
included, and not for a render without render flag `0x400`; a host whose pending count follows
the same rule (one per kick, none for such a render) has the two equal after every job, and every
cleanup completes (E314, scenes of one to four kicks, one run). The set's cleanup waits for
`executed_count` to equal the word dword 0 points at: one above or one below fails it, and with
dword 0 pointed at `executed_count` itself it completes (E315, one run; §6.3). Between the kicks
of an open scene RT data `state` bit 4 is clear and the context's pending list holds the render
details; the closing render sets the bit again (E314, one run).

Evidence: E156, E158, E159, E160, E161, E164, E304, E314, E315.

### 1.5 The PB descriptor

| dword | content |
|---|---|
| 0 | flags: bit 0 rebuild the page table, bit 1 reload the thresholds; the EDM clears both |
| 2, 3 | the initial free list: head/tail word and previous-page word |
| 4 | the DPM page-table base, low 4 bits ignored |
| 5 | `allocated_page_count`, written at each TA finish |
| 6, 7 | the current free list |
| 8, 9 | the local and global page counts |
| 10 to 13 | the TA, ZLS, global and PDS thresholds |
| 14 | the first block of the block list |

A block holds a page count in its dword 0, a first-page field in dword 2 and the next block in
dword 3. §6.1 gives how the EDM moves these words. The page table at dword 4 is one 32-bit entry
per page at the base plus four times the page number, the previous page in the high half and the
next in the low half, `0xffff` at both ends of the list; the DPM rewrites it in place as pages are
freed (§6.5).

Evidence: E156, E200, E201, E309.

## 2. Events and requests

Every event runs PDS #13, which hands the EDM's event task two words, `pa0` and `pa1` (E146). Each
handler tests a `pa1` bit and acknowledges with a write to `CR_EVENT_HOST_CLEAR` of a single status
bit, and in all seven tested bits the acknowledged status bit is 22 minus the `pa1` bit:

| `pa1` bit | acknowledged | event |
|---|---|---|
| 22 | `0x1` | `DPM_3D_MEM_FREE`: the 3D deallocation finished |
| 21, 20 | `0x6` | `DPM_OUT_OF_MEMORY_MT`, `_GBL` |
| 10 | `0x1000` | `TA_TERMINATE` |
| 9 | `0x2000` | `TA_FINISHED` |
| 7 | `0x8000` | `BREAKPOINT` |
| 4 | `0x40000` | `PIXELBE_END_RENDER`: the render finished |

`pa1` bit 8 starts the kernel CCB reader and writes no acknowledgement; bit 19 is tested with the
out-of-memory bits and posts nothing. The timer tick arrives in `pa0` bit 1. That `pa1` is
`CR_EVENT_STATUS` bits 22 to 0 in reverse order fits every pairing [infer]; E146's reading of
PDS #13's input as status bits at their own positions does not, and which events set bits 8 and 19
is open (Q033).

The handlers post work as request bits in `TA3DCtl` dword 31, and PDS #14 runs one of three tasks
for them (E146). A task never waits for another event: it ends, and work continues at the next
event or request; the only waits inside a handler are polls of status registers.

| request | posted by | handled by |
|---|---|---|
| `0x1` | `pa1` bit 22 | 3D memory free (§5.4) |
| `0x2` | `pa1` bit 4 | end of render (§5.4) |
| `0x8` | `pa1` bit 7 | the breakpoint handler |
| `0x10`, `0x20` | `pa1` bits 20, 21 | out of memory (§6.4) |
| `0x40` | `pa1` bit 10, and three other sites (E154) | TA terminated: the partial render (§6.4) |
| `0x80` | `pa1` bit 9, and the partial-render resume | TA finished (§4.5) |
| `0x20000` | a TA queue is not empty | the TA pick (§4.2) |
| `0x40000` | the transfer or 3D queue is not empty | the 3D schedule (§5.1) |
| `0x80000` | a partial render completed | the resume (§6.4) |

The EDM keeps one TA job and one 3D job in flight. `sa8` bit 0 is "TA running", bit 11 an
out-of-memory pending, and other bits, among them 5, 9, 10, 18, 19 and 22, belong to the
out-of-memory and partial-render paths (E160 lists them); `sa9` bit 0 is "3D running", bit 1 a
partial render, bit 2 a transfer, bit 4 a render in flight, bit 5 a deallocation pending, bit 6 an
out-of-memory waiting for the 3D. Contexts wait on lists held in secondary attributes, one list per
queue index: transfer `sa13`/`sa14`, TA `sa15`/`sa16`, 3D `sa17`/`sa18` (head, tail).

Evidence: E146, E154, E155; Q033.

## 3. The submit

The host writes a TA command at the CCB's write offset, advances the write offset by the command's
size and queues a kernel CCB command with kick address `0x11d` (E012) and the render context in
data dword 1. The handler (`0x11d`-`0x139`) reads only that dword: it adds 1 to the context's
`submitted_commands` and, if the count was 0 and the context has no pending render, appends the
context to the TA queue of its priority. It ends in the shared tail (`0x161`), which posts `0x40000`
when the transfer or 3D queue holds a context and `0x20000` when the TA queue does. The host never
passes the command's address: the TA pick finds it from the CCB base and read offset.

There is no 3D command. The kick table has no handler for a render (E012); the EDM queues the
render itself when a scene's last TA command finishes (§4.5).

Evidence: E012, E157, E165.

## 4. The TA path

### 4.1 Order of work

For one TA command the EDM runs, each step at a later event or request: the pick (§4.2) and the
kick (§4.3, §4.4) from request `0x20000`; the TA itself, started by the kick's last write; the TA
finish (§4.5) from `TA_FINISHED`. On a last kick the finish queues the render (§5).

### 4.2 The pick

The pick (`0x6f5`-`0x7b0`) returns at once while a cleanup is pending (`sa10` bits 1:0) or `sa8`
bit 2 or bit 18 is set. It walks the TA queue from the head; while a TA runs it looks only at
queue indices below the running one. A context is taken when all of these hold:

1. `submitted_commands` is not 0 and the context is not suspended;
2. the command at the CCB base plus the read offset has READY (dword 22 bit 0);
3. its TA transfer-queue sync is complete (each complete word equals its pending value), unless
   the first pointer is 0;
4. with `GEOM_FLAGS.TA3D_DEPENDENCY` (`0x400`), the dependency's write-complete word equals its
   pending value;
5. with TA flags `0x5` (first kick, or `0x4`), the RT data's `state` bit 4 is set;
6. the destination sync (command dword 15, unless 0) and every source sync are complete. These
   checks are skipped when the TA queue holds no other context (a lone context's TA starts with an
   incomplete source sync, E320); with a second context in the VM a command with an incomplete
   source sync is held back, even when the other context has nothing queued, and the other
   context's job completes (E450, three runs of each case; that its command is taken first is
   [infer]; the destination sync is open, Q034);
7. with `GEOM_FLAGS.PB_THRESHOLD_UPDATE` (`0x2000`): if the 3D runs, the pick ends; otherwise
   command dwords 10 to 13 go to PB descriptor dwords 10 to 13 and the descriptor's flag bit 1 is
   set, for the kick to apply.

If a TA runs, nothing starts. An RT data whose `state` has bit 6 (aborted), or render flag `0x2`
(`FRAG_FLAGS.ABORT`), takes the abort path (`0x80c`): the command completes (transfer-queue read
sync, TA status pairs, `SW_EVENT`, CCB advance) without running. Otherwise the kick starts.

Evidence: E161, E320, E450; Q034.

### 4.3 The kick, first half

The kick (`0x8e9`-`0x9b6`), in order:

1. `TA3DCtl` dword 27 = context, 24 = command, 26 = render details, 50 = the context's process id;
   the render details address also goes to RT data dword 1, so a host need not fill that field;
2. if `TA3DCtl` dword 25 names another RT data, its DPM state is stored through its own context's
   address space and its slot freed;
3. with `GEOM_FLAGS.FIRST_KICK` (`0x1`): `CR_SOFT_RESET` = `TA_RESET` (4), then 0;
4. the parameter buffer: if `TA3DCtl` dword 46 (the PB loaded for the TA) is already the context's
   PB, a pending threshold update is applied; otherwise the loaded one is stored and the context's
   loaded (§6.1), with the EDM's BIF index switched to the context's address space for the loads;
5. command dwords 142 to 169 are written to the registers below, one `str` each, in this order;
6. `CR_DMS_CTRL` bits 31:27 = command dword 5 as it is (`0x50000000` is 10 partitions);
7. the context's address space is mapped for the TA; with the new-context flag the flag is cleared
   and the caches invalidated;
8. invalidations by TA flag: `0x40` the data cache (`CR_CACHE_CTRL` bit 28), `0x20` the PDS caches,
   `0x10` `CR_USE_CACHE` (`0x0a08`) = 1.

| command dwords | registers, in order |
|---|---|
| 142 to 144 | `CR_TE_AA` (`0x0204`), `CR_TE_MTILE1` (`0x0208`), `CR_TE_MTILE2` (`0x020c`) |
| 145 to 147 | `CR_TE_SCREEN` (`0x0210`), `CR_TE_MACROTILE_STRIDE` (`0x0214`), `CR_TE_PSG` |
| 148, 149 | `CR_VDM_CTRL_STREAM_BASE` (`0x0238`), `CR_MTE_CTRL` (`0x023c`) |
| 150, 151 | `CR_TE_PSGREGION_ADDR` (`0x021c`), `CR_TE_TPC_ADDR` (`0x0220`) |
| 152 to 154 | `CR_MTE_RHW_MIN` (`0x0240`), `CR_MTE_RHW_CLAMP` (`0x0244`), `CR_PPP_SCREEN` |
| 155 to 157 | `CR_USE_REG_0A04`, `CR_USE_REG_0AA0`, `CR_BIF_TA_REQ_BASE` (`0x0c90`) |
| 158 to 163 | `CR_TA_REG_02B0`, `CR_TA_REG_02D4`, `CR_TA_REG_02D0`, `CR_TA_REG_02B4`, `CR_REG_0324`, `CR_REG_0368` |
| 164 to 166 | `CR_REG_0364`, `CR_REG_0370`, `CR_REG_0374` |
| 167, 168 | `CR_DPM_REG_074C` (`0x074c`), `CR_TE_REG_02A8` |
| 169 | `CR_MTE_MULTISAMPLECTL` (`0x0230`) |

The words are copied, so the firmware gives no field layout for them; §7 gives what the hardware
shows.

Evidence: E159.

### 4.4 The kick, second half

1. *DPM slot* (`0x9b7`-`0x9f6`). The DPM holds two contexts; `TA3DCtl` dwords 20 and 21 record the
   RT data owning each. The TA takes the slot that holds its RT data, else a free one, else the one
   the 3D is not using, storing a different previous owner first. The slot goes to bit 2 of
   `CR_DPM_STATE_CONTEXT_ID` and the RT data to `TA3DCtl` dword 25. Bit 2 is the TA's slot and,
   by the 3D kick's use, bit 1 the 3D's [infer] (Q064); the register reads 0 at every sample
   while jobs run, so it cannot show the slot (E409). On the hardware dwords 20 and 25 hold
   the RT data from a scene's geometry kick to its closing render, which clears them (E314, one
   run). A first kick whose RT data has the address a gone context left in dword 20 (render flags
   `0xc`) renders exactly and clears it (E316, one run). A first kick on a second context, whose RT
   data lies at another address, leaves a dword 20 kept by bit 2 alone as it is and clears the words
   that bit 3 keeps, alone or with bit 2 (read after the pair of renders in E451, and between the
   renders and after the second in E458, two runs of each); a second context that keeps too takes
   dword 21 after a first kept by bit 2 alone, and the words 20 and 25 after one kept by `0xc`
   (E451). With the first context closed after its render, the kept words stay (E458) and a second
   context's render leaves a dword 20 kept by bit 2 alone as it is and is exact, while after bit 3
   it faults at page `0x20003000` (6 of 6 runs, Q036, Q045).
2. *Clear* (TA flags `0x1` or `0x8`, `0xa0e`-`0xa60`). Bit 0 of `CR_DPM_STATE_CONTEXT_ID` gets the
   slot; RT data dword 5 goes to `CR_DPM_STATE_BASE0` or `_BASE1`, dword 6 to `CR_DPM_CONTROL_BASE`;
   for each render target `(index << 3) | 2` goes to `CR_DPM_TASK_STATE` and `CR_DPM_TASK_CONTROL`
   (task 2 clears, 1 stores, 4 loads); a store and a load task follow whose index comes from
   `0x0740` bits 17:9, each only if that field is not 0; then RT data dword 7 goes to
   `CR_MTE_OTPM_BASE` and the value 9 to `CR_MTE_OTPM_OP`. What the two `0x0740` tasks do is not
   shown.
3. *Reload*. With neither flag, an RT data not already in the slot is loaded (state, control and
   OTPM) through the TA's address space. A zero result of the mask `0x9` is what runs these calls
   (E172).
4. *State*. `CR_TE_CONTEXT_STATE` (`0x0274`) = render details dword 73, on every kick. `CR_TE_PSG`
   is read and `0x01000000` ORed in, and `0x00200000` too when RT data `state` bit 8 is set (the
   kernel poke rtds:19 flips it; E424). Bit 21 makes the TA set bit 29 of word 0 of every target
   region header (§10.2), as the state bit does; what that mark does, and what bit 24 does, is not
   shown. The register reads `0x01400000` after every unpoked job and drops to `0x00400000` for 17
   us at each kick (E409); the command's word at 0 faults the job, and that this is for want of the
   kernel's bit 22 is a reading [infer: one value, 0] (E305, one run; Q064).
5. *Marks*. With TA flags `0x1` or `0x4`, RT data `state` bits 11:4 are cleared and the RT status
   words zeroed.
6. *Running*. `sa8` bit 0 is set and the context moves to the head of its TA queue.
7. *Copy* (`0x7b1`), command to render details: render flags to dword 53; with render flag
   `0x200` the dependency (68, 69) to 63, 64; frame number to 80 and `TA3DCtl` dword 41; the 3D
   transfer-queue sync (29 to 32) to 57 to 60, then dword 15 over 56; the source syncs to 90 on;
   dwords 18, 19, 20 to 72, 70, 71; `pds_bgnd` to 76 to 78; the 3D status pairs to 81 on. The patch
   pairs are applied as memory writes.
8. *Start*. With TA flag `0x1000`, HostCtl dword 16 = 500. The kick's last instruction (`0xacc`)
   writes 1 to `CR_VDM_START` (`0x0200`): the TA starts, on the VDM stream at
   `CR_VDM_CTRL_STREAM_BASE` [infer]. The instruction number is not the register `0x0acc`
   (`CR_EVENT_TIMER`), which the kick never writes.

Evidence: E158, E172, E305, E409, E424; Q064.

### 4.5 The TA finish

`TA_FINISHED` posts `0x80`. With `sa8` bits 9 and 10 clear (no partial render pending; E156 has
the other cases) the handler (`0x643` on):

1. clears `sa8` bits 0, 2, 3, 4 and 7 to 10 (the TA is idle) and READY in the command;
2. completes the TA transfer-queue read sync (read pending + 1), if its address is set;
3. stores the upper half of `CR_DPM_PAGE_STATUS` (`0x0724`) in the PB descriptor's
   `allocated_page_count`;
4. writes the TA status pairs, `*address = value`;
5. raises `SW_EVENT`: `CR_EVENT_STATUS` = `0x4000`, the host interrupt;
6. with `GEOM_FLAGS.LAST_KICK` (`0x2`): sets RT data `state` bit 5; unless render flag `0x8`
   (`FRAG_FLAGS.NO_DEALLOCATE`), clears `TA3DCtl` dword 25 and writes `CR_TE_TPCCONTROL` =
   `0x40000000`, waiting for `CR_EVENT_STATUS` bit 10;
7. with TA flags `0x5`: appends the render details to the context's pending list [infer];
8. unless a last kick without `NO_DEALLOCATE`: saves `CR_TE_CONTEXT_STATE` in render details
   dword 73, so the scene's next kick resumes the tiling engine. A kick that is not a last kick
   also adds 1 to the RT data set's `executed_count` and goes to step 10 (on the hardware the
   count rises by one with each geometry kick, E314, one run);
9. a last kick: with render flag `0x1` (`FRAG_FLAGS.NO_RENDER`) the scene's memory is freed first
   (`CR_DPM_FREE_CONTEXT` = 1, `CR_TE_TPCCONTROL` = `0x80000000`); with TA flag `0x1000` HostCtl
   dword 16, which the kick set to 500, is cleared; then the render details move from the pending
   list to the ready list and, if that list was empty, the context joins the 3D queue;
10. posts `0x40000` if the transfer or 3D queue holds a context; advances the CCB read offset by
    command dword 0 modulo 64 KiB and subtracts 1 from `submitted_commands`; re-queues the context
    if it has more commands or pending renders, and posts `0x20000` if the TA queue is not empty.

On the hardware `TA3DCtl` dword 24 reads the TA client CCB's base (`0x32400000`) after one render
of a new context and `0x2c0` more for each further render, up to `0x32400840` after four: the
address of the last TA command read, the CCB's read address advancing by a command of `0x2c0`
bytes [infer: one to four renders] (E303).

Evidence: E156, E184, E303; Q065, Q119.

### 4.6 What starts a render

A render exists in the firmware when a TA command with `LAST_KICK` finishes: the finish queues it
(§4.5 step 9), and so does the abort path of the pick for a last kick. A command without the flag
queues nothing. Render flag `0x400` is tested once, in the render's completion, where it adds 1 to
`executed_count`. One command carrying both `FIRST_KICK` and `LAST_KICK` runs the first-kick
actions at its kick and the last-kick actions at its finish through the same code as two commands
would; nothing compares the two flags or the command's place in the CCB [infer] (Q119).

The hardware agrees: a kick without `LAST_KICK` leaves its render waiting and the job hangs; a
scene accumulates the geometry of several kicks and the kick that ends it renders all of them; a
render empties the scene for the next kick (E051 to E053; render_uapi.md §8.5).

The render flags the firmware tests: `0x1` `NO_RENDER`, `0x2` `ABORT`, `0x4` (only inside the mask
`0xc` at completion, §5.4), `0x8` `NO_DEALLOCATE`, `0x10` (§11.5), `0x20` `GET_VIS_RESULTS`, `0x80`
`DEPTH_BUFFER`, `0x100` `STENCIL_BUFFER`, `0x200` `TA3D_DEPENDENCY`, `0x400`, and the bits from 14
up, which the completion copies into RT data `state`. On the hardware, in a kernel-built triangle
job, render flag bit 0 hangs the job, bits 1 and 4 complete it with no pixel, and bits 5 and 9 fault
(E050). Held, the job with bit 0 has finished its TA and the 3D has taken the render
(`hw_render_details_3d` names it, both frame numbers 1), which never completes: its executed count
stays 0 and RT data `state` reads 0x20 (E361, one run). What the 3D waits for, when the firmware
completes a `NO_RENDER` render without rendering (§5.1), is not shown (Q065). With bit 10 (`0x400`)
clear the render is drawn and adds nothing to `executed_count`; its RT data set's cleanup completes
when the host's pending count leaves it out too, and never completes when the host counts it (E303;
E314, one run; §6.3).

Evidence: E050, E051, E052, E053, E164, E165, E166, E303, E314, E361; Q065, Q119.

## 5. The 3D path

### 5.1 Scheduling

Request `0x40000` runs the schedule (`0x1035`). It returns at once on a pending cleanup or with
`sa9` bit 1 or bit 3 set, or while a transfer runs; while a render runs it looks only at queue
indices below the running one. For each index it tries the transfer pick, then the 3D pick; the
first kick ends the schedule.

The 3D pick walks the 3D queue. A suspended context is skipped, unless it is the TA's current
context with an out-of-memory pending, whose render may free memory. It takes the first render
details of the ready list and checks the destination sync list entry of the render-target index
(list + 8 + 16 x index; both complete words; unless the list address is 0), the 3D transfer-queue
sync and every source sync. With RT data `state` bit 6 or render flags `0x3` it completes the render
details without rendering (syncs, scene routine, schedulers); otherwise it kicks.

Evidence: E165.

### 5.2 The kick

The kick (`0x112b`-`0x12db`), in order:

1. `TA3DCtl` dword 51 = process id, 30 = render-target index, 29 = render details, 42 = frame
   number;
2. *DPM slot*, as for the TA (§4.4) with bit 1 of `CR_DPM_STATE_CONTEXT_ID`. A previous owner is
   stored only if its scene has ended (RT data `state` bit 5). The RT data's context is loaded
   through the 3D's address space (`CR_BIF_BANK_SET` bit 9), or, when it is already in the slot,
   only the 3D's address space is mapped;
3. *parameter buffer*: unless `TA3DCtl` dword 47 (the PB loaded for the 3D) is the context's,
   the old one is stored and the context's loaded (§6.1);
4. *deallocation*: render flag `0x8` clear, `CR_DPM_3D_DEALLOCATE` (`0x063c`) = 3 and `sa9` bits 4
   and 5 set (render and deallocation both pending); set, 0 and only bit 4;
5. `CR_ISP_VISIBILITY_CTRL` = `0xff`; `0x040c`, `0x0410` and `0x0404` = 0;
6. render details dwords 0 to 51 are written to the registers below, one `str` each, in this order;
7. `CR_DPM_3D_RT_INDEX` (`0x073c`) = the render-target index *i*; for *i* > 0, `0x0408` gains
   *i* x RT data dword 11, the Z load and store bases *i* x render details dword 70 and the
   stencil bases *i* x dword 71; if `rt_patch_dev_vaddr` is set, the two dwords at the patch list
   + 8*i* are written there, through the 3D's address space;
8. with render flag `0x10`, `CR_ISP_ZLSCTL` bit 0 is set (§11.5); `CR_DMS_CTRL` bits 26:22 = render
   details dword 79; `CR_DPM_PARTIAL_RENDER` = 0 (§6.4);
9. the data cache is invalidated, `0x043c` and `CR_USE_CACHE` set to 1, the PDS caches
   invalidated;
10. `CR_ISP_ZLSCTL` is adjusted from render flags `0x80` and `0x100` and the RT status word's bit 1
    (§11.5);
11. the background object's first three words are written (§5.3);
12. `TA3DCtl` dword 28 = RT data, `sa9` bit 0 set, the context to the head of its 3D queue, and
    `CR_ISP_START_RENDER` (`0x0428`) = 1 (`0x12da`).

### 5.3 The background object

After the register block and before `CR_ISP_START_RENDER`, the kick switches the EDM's BIF index to
the 3D's address space and writes three words of the background object at RT data dword 4: dwords
0 and 1 from render details dwords 76 and 77 (`pds_bgnd`, copied from the TA command), dword 2 from
the word at render details dword 69 + 4 x the render-target index. Nothing tests that the list
address is not 0. What the three words mean to the ISP is not shown by the firmware (Q066).

The object's coordinate words, on the hardware, in a transfer copy's background object of two
layers: with the tag's size field raised from 2 to 4, the coordinate dwords are read vertex by
vertex, layer A's `(u, v)` then layer B's; read layer by layer the same words give other images,
and with the size field left at 2 they are not read as two layers. The format word after the
coordinates changed nothing over eight values from 0 to `0xffff`; `0xffffffff` makes every pixel
sample texel (0, 0). Neither byte of a one-layer copy's word at that place changes the copy (E069).
The other words of a render's background object are not established yet (Q066).

`CR_ISP_BGOBJVALS` (`0x04bc`), the render details' dword 17, decides whether the background object
is drawn: with its bit 9 clear the pixels the scene does not cover keep earlier contents (E216;
§11.3 has its low bits).

Evidence: E069, E162, E209, E216; Q066.

### 5.4 Completion

A render completes when both the end of render (request `0x2`) and the 3D deallocation (request
`0x1`) have arrived, in either order: each handler clears its `sa9` bit (4 or 5) and completes only
if the other is already clear. The end-of-render handler first sends a transfer to its own
completion (`sa9` bit 2; transfer.md §3.3) and waits on the clock-gating registers. The completion
(`0xfd1`):

1. clears `sa9`; if an out-of-memory was waiting for the 3D, writes `CR_DPM_OUTOFMEM` = 1; a
   partial render posts `0x80000` instead and ends (§6.4);
2. with `GET_VIS_RESULTS`, accumulates the visibility counters;
3. sets the destination sync entry of the render-target index complete (write pending + 1). With
   more render targets left it steps to the next index and the render details stay queued for it.
   On the last it completes the TA to 3D dependency, the 3D transfer-queue read sync, every source
   sync's read sync, and writes the 3D status pairs; in all cases bit 0 of that index's RT status
   word is set;
4. on the last index: RT data `state` = (old with bits 6:5 clear) | `0x10` | ((render flags >> 14)
   << 12), free again; with render flag `0x400`, `executed_count` + 1 in the RT data set of render
   details dword 54 (on the hardware the count follows dword 54, E304, one run); RT data dword 1
   cleared; unless render flags `0xc`, the word at render details dword 52 cleared and the RT data's
   DPM slot freed; the word the destination sync list's first dword names cleared;
5. raises `SW_EVENT`, after each render target;
6. the render details leave the ready list (after the last index), the context the 3D queue
   (re-queued if more renders are ready), and the TA and 3D schedulers run again.

The HWPerf records of these paths have type 2 for a transfer, 3 for the TA, 4 for a render and 8
for a partial render, with bit 28 set in an end record (§13).

On the hardware either bit of the mask `0xc` keeps the slot: after a render with `0x4`, `0x8` or
`0xc`, `TA3DCtl` dword 20 still holds the RT data once the context is cleaned up, and with `0x8`
dword 25 too (the TA finish keeps it, §4.5); without them both are 0, and a later render with the
bits clear clears dword 20 again (two runs). A later job on a context at another address, with the
bits clear, leaves the word kept by bit 2 alone and clears the words kept by bit 3, which held the
first context's RT data between the renders and read 0 after the second's (E451, E458); with the
first context closed first, the word kept by bit 2 stays and the render is exact, while after bit 3
the render faults at page `0x20003000`, in the second context's TA data where the DPM state page of
a 64 x 64 context lies [infer], and the close leaves the words in place (E458, Q036, Q045). The
DPM status registers show the kept owner too: after a render with bit 3, `0x0700` and `0x070c` read
`0x04220003`, `0x0710` and `0x071c` `0x421`, `0x0724` `0x00020002` and `0x0728` 2, against
`0x00020003`, 1, 0 and 0 after bit 2 alone or no flag (6 of 6 runs each); the close changes none of
the 85 registers `0x0600` to `0x0750` (4 of 4 runs with bit 3, and none in the 4 runs with the
control and bit 2 alone), the second context's render then faults (9 of 9 runs) with none of the 85
changing before the recovery (3 of 3 runs that sampled them all), and with the first context open it
takes them back to `0x00020003`, 1, 2 and 0 (5 of 5; E462).

Evidence: E164, E303, E451, E458, E462; Q036, Q045.

## 6. Parameter buffer and DPM

### 6.1 Loading and storing a PB

The EDM keeps a PB loaded on each side: `TA3DCtl` dword 46 for the TA, 47 for the 3D.

- *Load into the TA* (`0x16a2`): descriptor dword 4 (low bits cleared) to
  `CR_DPM_TA_ALLOC_PAGE_TABLE_BASE` (`0x0618`), dword 6 to `CR_DPM_TA_ALLOC_FREE_LIST` (`0x061c`),
  dword 7 to `CR_DPM_TA_ALLOC` (`0x0648`), dwords 8 and 9 (the second in the high half) to
  `CR_DPM_TA_PAGE_COUNTS` (`0x0638`), the thresholds to `CR_DPM_TA_PAGE_THRESHOLD` (`0x0620`),
  `CR_DPM_ZLS_PAGE_THRESHOLD` (`0x0624`), `CR_DPM_TA_GLOBAL_LIST` (`0x0628`, low 16 bits with bit
  16 set) and `CR_DPM_PDS_THRESHOLD` (`0x0668`); `0x0664` gets which pairs of the three PB slots of
  `TA3DCtl` (dwords 46 to 48) differ; then `CR_DPM_TASK_TA_FREE` (`0x0684`) = 1, waiting for bit 0
  of `0x0118`.
- *Load into the 3D* (`0x16e9`): the same fields to `CR_DPM_3D_PAGE_TABLE_BASE` (`0x0600`),
  `CR_DPM_3D_FREE_LIST` (`0x0604`), `CR_DPM_3D` (`0x064c`), `CR_DPM_3D_PAGE_COUNTS` (`0x0660`), then
  `0x0664`, and `CR_DPM_TASK_3D_FREE` (`0x0680`) = 1.
- *Store* (`0x168d` TA, `0x16d4` 3D): the free-list status registers back into dwords 6 to 9.
  When both sides share a descriptor the other side is stored first with its pipe paused (§6.2).
- *Thresholds* (`0x1665`): with flag bit 1 the four thresholds are reloaded and flag bits 1:0
  cleared.
- *Page table* (`0x170d`): with flag bit 0 the EDM copies dwords 2 and 3 over 6 and 7, zeroes 8
  and 9 and walks the block list, writing one entry per page at the table base, each holding the
  previous page in the high half and the next in the low half, `0xffff` for the missing neighbour
  at both ends. The store offset is four bytes a page from the base, measured with the context's
page writable (E446).

On the hardware, with the descriptors our kernel fills (page counts from `0x422` down to `0x40`),
the registers read back as these loads leave them: the free list `0x04220001` at `0x422` pages (tail
`0x422` in the high half, head 1), the previous-page word the page count less one in the high half,
the TA threshold the page count + `0x10`, the ZLS threshold the page count - `0x22`,
`CR_DPM_TA_GLOBAL_LIST` that with bit 16, `CR_DPM_PDS_THRESHOLD` the page count - `0x122` (0 below
it), `0x0664` = 5, and the page-table base the same at every size. Our kernel builds the page table
itself, and the DPM works on it: after every job the table in memory still chains all the PB's
pages, edited in place one entry per page at base + 4 x page, and the free-list status registers
agree with it (§6.5). The EDM's own builder (flag bit 0, set by a kernel poke at the first kick)
faults at once on a write to the render context's page, which the client's directory maps read-only
(E362, two runs). With that page writable for the context (the kernel's debugfs `alias_ctx_rw`), a
64x64 render with flag bit 0 is exact and no fault comes; with the page-table base aimed at zeroed
scratch pages 1058 dwords change, one for each of the 1058 pages and none past them, the first at
dword 1, and moving the base by 0x1000 or 0x2000 moves them as much, so the entry of page i is at
the base + 4i; on the kernel's own table the result after the job equals that of a job without the
flag (E446; three runs of each). With the same base and flag bit 0 clear (left alone or poked to 0)
the render faults on the empty table in 6 of 6 runs and 0 to 2 scratch dwords change, so the stores
need the flag; with the table at scratch pages the host filled with the table the kernel builds
before a job the render completes and changes 4 dwords only, with the flag clear or set (E453, 6 of
6 runs each), so the flag's action makes the 1058 stores [HW], over zeros only. After a fault of the
base alone over a zero table exactly the next two jobs fault, whatever they are, with a debugfs GPU
reset between the jobs or without (E463, Q036).

Evidence: E200, E201, E309, E362, E446, E453, E463; Q036.

### 6.2 The settle routine

Before a PB swap on a pipe that is running (from the TA kick, the 3D kick and one other site), the
routine at `0x15bc` sets `CR_DMS_CTRL` bits 2:0 and waits for the other pipe to go quiet: for the 3D
it reads the four ISP signature registers (`CR_ISP_SIGNATURE0` to `3`: `0x04d4`, `0x04d8`,
`0x0518`, `0x051c`), then
`CR_SETTLE_POLL0` and `CR_SETTLE_POLL1` (`0x0308`, `0x030c`), each set twice 1000 loop counts
apart until the two xors agree; for the TA it does the same with `CR_PPP_SIGNATURE` (`0x026c`),
`CR_TE_DIAG2` and `CR_TE_DIAG5`. It then polls the USE service registers. The release
(`0x15ad`) clears `CR_DMS_CTRL` bits 3:0 when its nesting count returns to 0. No firmware
instruction writes any of the polled registers. That the routine waits for idleness is a reading
of where it is called and what it polls [infer] (Q036).

Evidence: E153; Q036.

### 6.3 The render-context cleanup

The kernel command CLEANUP (E012) reaches the render-context routine (`0x39d`), which waits until
the context's pending list, ready list and `submitted_commands` are empty. Then, only with flag
bit 5 of the context set, it clears `TA3DCtl` dword 46 or 47 when they hold the context's own PB.
With the bit clear the slots keep the PB until the PB's own cleanup (`0x475`), which clears them
whatever the flags. Bit 5 is tested nowhere else on a context's flags.

The hardware agrees (`CONTEXT_FLAGS.OWN_PB`). With the context's PB loaded in both slots, a
cleanup of a context with flags `0x20` leaves the slots holding it after the render-target step,
and they read 0 after the render-context step; with flags 0 they still hold it then, and read 0
only after the PB step. A context whose PB is not the one loaded leaves the slots alone with the
bit set. Two contexts sharing one PB were not tried.

Before the context's own steps the RT data set is cleaned up. That step waits for the set's
`executed_count` to equal the word its dword 0 points at, the host's pending count (§1.4): read on
the hardware, the counts are equal after every job when the host counts one per kick and none for a
render without render flag `0x400`, and every cleanup completes (E314, one run); one above or one
below, the step never completes and our kernel times out (0.5 s) and resets the GPU (E315, one run).
The failures of E303 and E304, a render with `0x400` clear and every scene of two kicks, were a host
that counted one per scene. After a cleanup `TA3DCtl` dword 32 holds the PB descriptor the cleanup
names, which in every case tried is also the context's (`cleanup_pb_desc`; the name rests on the
dataflow, which writes it from the cleanup command [RE]). Dword 49 (`render_context_count`) moves by
one at each context's first kick, whatever its renders, and not at its later kicks or its cleanup; a
first kick that faults at its PB load has already moved it (E314, E316, E319, one run each). It runs
from 0 to `0xe` and goes from `0xe` to 0 at a context's first kick with no reset (twice, E314 and
E316), and after a reset it reads 0 (E315). It is the bus interface directory list the kick gave the
context's page directory: the k-th first kick after a reset writes the directory into
`CR_BIF_DIR_LIST_BASE1` to `BASE14` (k 1 to 14) or `BASE0` (the 15th), `BASE15` keeping the EDM's
own, and the dword reads k mod 15; a kick whose directory another context's kick has evicted takes
the next list, and a live context loses nothing by it (E360, 14 and 16 contexts alive; Q076). What
the context's own steps wait for beyond its lists is open (Q029). A context that shares a PB
(debug option) sends its RT and RC cleanups with a zero PB descriptor and no PB step; the donor's
cleanup, with the PB step that clears the loaded-PB slots, runs after the sharing context's release
whichever is closed first (E449).

Evidence: E167, E168, E303, E304, E314, E315, E316, E319, E360, E449; Q029, Q076.

### 6.4 Out of memory and partial renders

The firmware's path (`pa1` bits 20 or 21, handler `0xb50`; `sa8` bit 19 is set for bit 20 and
cleared for bit 21): it sets `sa8` bit 11. If the 3D is idle and the context has a ready render,
it waits for that render. Otherwise, unless a partial render is under way (`sa8` bit 5), it counts
the signal in `num_out_of_mem_signals` and sets RT data `state` bit 7; if the 3D runs it waits for
it, and if the 3D is idle it waits while the destination sync entry of the macrotile's render
target or a source sync is not complete (`0xb0b`). Then two decisions follow.

- *The kind of list*, only when bit 0 of `0x0734` is clear. For `pa1` bit 21 (`sa8` bit 19 clear)
  it grows the TA's share of the global list (`CR_DPM_TA_GLOBAL_LIST`), sets `sa8` bit 22 and
  restarts with `CR_DPM_OUTOFMEM` = 1; for bit 20 it writes back the global list a grow saved,
  clears `sa8` bit 22 and goes on to the second decision.
- *Raise or abort* (`0xbbf`), by `sa8` bits 7 and 9 and the page counts an earlier abort saved.
  With bit 7 set, bit 9 clear and the saved count smaller than the current one, it raises
  `CR_DPM_ZLS_PAGE_THRESHOLD` by `0x20` and restarts. Otherwise it aborts the macrotile:
  `CR_MTE_OTPM_OP` = 1, `CR_DPM_ABORT_STATUS_MTILE` saved in `TA3DCtl` dwords 39 and 40,
  `CR_DPM_OUTOFMEM` = 4, `CR_DMS_CTRL` bit 0 set. The TA then stops (`TA_TERMINATE`).

The terminate handler (`0xc23`) counts the render in `num_spm_renders` and, once the 3D is idle,
writes the render details' register block as the 3D kick does, except that the region header base
is offset to the aborted macrotile's render target, `CR_ISP_PARTIAL_REGION_BASE` is derived from
the saved abort status and RT data dword 2, and `CR_DPM_3D_DEALLOCATE` is 2 or 3; it then starts
the render. Its completion posts `0x80000`, and the resume (`0xdbf`) clears the DPM control state
(`CR_DPM_TASK_CONTROL` = 2), sets bit 1 of the macrotile's RT status word and restarts the TA with
`CR_DPM_OUTOFMEM` = 1. That bit 1 means "depth stored, load it in the final render" is a reading
[infer]; the 3D kick does read it to adjust the ZLS control (§11.5). The only host inputs named in
this path are the PB descriptor's thresholds. What the thresholds, the global list and the page
counts mean to the DPM is not shown.

`CR_DPM_PARTIAL_RENDER` (`0x0658`) is written only by the firmware: 1 in the partial-render
routine, 0 in its resume and in every 3D kick, never read; `CR_DPM_SPM_SWITCH` (`0x065c`) is
written 1 then 0 inside the same two routines. On the hardware `CR_DPM_PARTIAL_RENDER` reads 1 in
stretches during a job that overflows its PB, and never in a job that does not: at 4096 x 4096, 1
to 10 stretches of 26.8 to 28.9 ms as the PB shrinks from `0x100` to `0x23` pages; at 1024 x 768,
one stretch of 1.0 to 1.2 ms from `0x30` pages down. That each stretch is one partial render is a
reading of the firmware [infer]. `CR_DPM_SPM_SWITCH` was never seen at 1. So
`CR_DPM_PARTIAL_RENDER` is a flag the EDM raises while a partial render runs [infer]; that a host
write to it would enable anything is not tested.

A scene larger than its PB completes with no fault or hang. The 4096 x 4096 triangle draws only
part of the image from `0x100` pages down, the 1024 x 768 one from `0x30` to `0x24` pages; at 1024
x 768 with `0x23` pages the job overflows yet the image is exact. The image is the same in both
repeats of each size, and the amount drawn does not follow the PB size. The missing pixels are
painted over (E311, one run): with `CR_ISP_CTL.PROCESS_EMPTY_TILES` clear every overflowing job
draws the whole triangle at every buffer size, so no geometry is discarded. With the kernel's value
the missing pixels are whole regions of the macrotiles that held geometry at a partial render,
painted with the background by the final render, whose streams hold only what was tiled after the
last partial render. The amount drawn is therefore the geometry tiled after the last partial
render. At 1024 x 768 in `0x23` pages the image is exact: the ZLS threshold is 1, and `TA3DCtl`
dword 35 (page status less 2) reads `0xffff` after the job, so its last abort came at the first
page, before any region holds geometry [infer] (E310, one run). A scene needs a colour (and depth)
reload in its background object to survive a partial render: a background shader that fetches the
render target at the pixel's position (position from a `douti` of source 0 with two components)
gives the whole triangle of the 4096 x 4096 job in `0x100` pages, 4422528 pixels, where the
library's background leaves 987008 (E442, three runs each); the depth reload is not run (Q038).
With a depth buffer the same jobs change (E461): the ZLS store of this setup writes a window of the
buffer, 64512 dwords at 1024 x 768 and 326656 at 4096 x 4096, whatever the buffer (§11.6; E465);
a job that overflows leaves the window's first 15104 dwords (80640) at 0.0 and, from `0x28`
pages down at 1024 x 768, the rest as the depth with its sign bit set (-1.0, -0.5): with no two
tiles at one address the stores are zeros for the first row of macrotiles (tile rows 0 to 11) and
the ramp negated for the rest, at 0x28, 0x23 and 0x30 pages for the ramp job (E468; Q107; E461's
z = 0.5 job at 0x30 keeps positive values and the difference is not explained). The triangle is
drawn on 0, 27408, 31629 and 31629 pixels at `0x30`, `0x28`, `0x24` and `0x23` pages against
51408, 162544, 205061 and 207456 without the buffer. The render node reports such a job as an
overflow (render_uapi.md §8.6).

On the hardware a partial render runs as follows (1024 x 768 in `0x30` pages; E310 and E312, one run
each). The TA stops with page status `0xe` and `CR_DPM_ABORT_STATUS_MTILE` reading the aborted

## 9. MTE state

The vertex side delivers, per object, a state block the MTE reads and per-vertex outputs; the
encoding of the VDM stream's blocks and of the state block's presence word is not established yet
beyond the fields below (Q069). Field names are the glossary's (`VIEWPORT`, `MTECTL`, `OUTSEL`);
`blk:n` in the records is word *n* of the triangle's state block.

### 9.1 Viewport

`VIEWPORT.X_OFFSET`, `X_SCALE`, `Y_OFFSET` and `Y_SCALE` (vp0 to vp3, IEEE singles, 32.0 for the
64 x 64 target) scale and place the triangle; a negative y scale mirrors it. Which pair is x and
which y rests on that one mirror (E061). The depth is `Z_OFFSET` + `Z_SCALE` x z: with the z
offset at 0.75 and z set to the clip x, the triangle draws exactly the pixels whose clip x is
below 0.5 against a background depth of 1.0, so vp5 is the z scale (0.5) [infer: the two constants
are not fixed separately]. On a flat triangle the depth is the z offset alone [infer] (E066).

The MTE clips at clip z = -w and z = w: at w 1 a flat triangle draws whole from z -1 to 1 and is
removed at -1.01 and 1.01, and a sloped one (z = 2x, 4x, 2x + 1, 2x - 1) is cut along the line
where its z reaches -1 or 1. The depth the viewport then makes is not clipped: with the z offset
anywhere from -0.5 to 1.5 the flat triangle draws whole under depth always. Against a clear depth
a depth above 1 compares as itself (1.01 and 1.5 pass greater than 1.0) and a negative one as 0
(-0.01 and -0.5 fail less than 0.0 and pass less than 1.0) [infer: a clamp of the negative side
only, from two values each side, one run] (E287).

The depth compare is exact to the ulp: against a loaded depth of 0.5 + *n* ulp, depth test less,
a triangle at 0.5 is removed at *n* = 0 and drawn from *n* = 1 up, with `CR_ISP_LINE_SAMPLE_POS` at
0 and 1 alike.

Evidence: E061, E066, E072, E193, E287.

### 9.2 MTECTL

- Bits 1:0 cull one winding (1 the triangle as drawn, 2 the mirrored one) or neither (0, 3)
  (`MTECTL.CULL_MODE`); bits 2 to 5 and 7 change nothing on an unclipped triangle (E062).
- Bit 6 (`MTECTL.NO_TRANSFORM`): the MTE takes the vertex x and y as window coordinates in pixels,
  with no division by w and no viewport. A w of 2 changes neither the image nor the object's vertex
  words, and the object's 1/w dwords then hold w itself [infer: no dump with the bit clear at w 2].
  On the job's triangle, whose clip coordinates are below 1, the bit removes it (E062).
- Bits 8:7 (`MTECTL.FLAT_VERTEX`) choose which vertex's values the clipper gives the vertices it
  makes: 0 interpolated values, 1, 2, 3 vertex 0's, 1's, 2's. A non-zero 2-bit field from bit 10
  (`MTECTL.ATTR_SMOOTH`) returns its attribute to interpolation. On an unclipped triangle no value
  tried changes the image. Which attribute each field governs is read from the colour and the
  first coordinate only.

Evidence: E062, E195, E196.

### 9.3 The w clamp

The triangle's size goes as 1/w (261 pixels at w 2, 1062 at 1, 3212 at 0.5, the whole 64 x 64
target from w 1e-3 to 1e-5), and below 1e-5 it shrinks away (395 pixels at 2e-6, 1 at 1e-7, none
at 0 or a negative w). The threshold is the state block's w clamp word (1e-5 in the job) [infer:
four values of the word]: at 1e-3 it removes the triangle at w 1e-5 and below; at 1e-7 or 0 the
triangle stays whole down to 5e-7.

Evidence: E194.

### 9.4 Output select, coordinate sets and clip planes

`OUTSEL.VTX_SIZE` (bits 19:16) is the vertex's size in dwords (4 for a position). Giving the
vertices a coordinate set takes three words changed together: the vertex size (4 to 6), the
coordinate-size word (0 to 2), and the vertex task's output size (`VDM_TASK1.OUTPUT_SIZE`, bits
31:24 of the task's second word, 1 to 2 rows of four dwords). With the vertex size alone the
triangle keeps 490 of its 1062 pixels; with the output size alone at another value it is removed.

The coordinate-size word (`COORDSIZE.SET_LAYOUT`, state-block word 16) holds three bits per set
from bit 0, the components that set has in the vertex. With a vertex writing x, y, 0.25 and 0.5
after the position and four components iterated, one set reads:

| field | components read |
|---|---|
| 1 | x, 0, 0, 1.0 |
| 2 (6 and 7 read as 2) | x, y, 0, 1.0 |
| 3 | x, y, 0.25, 1.0 |
| 4 | x, y, 0, 0.25 |
| 5 | x, y, 0.25, 0.5 |

So 1 is x, 2 xy, 3 xyz, 4 xyw (the third dword read as w) and 5 xyzw; a missing component reads
0, or 1.0 for the fourth [infer]. Two sets take the vertex's dwords in order, each as many as its
field says (`0x19` reads x, then y 0.25 0.5); a field of 0 reads as 2, so the vertex size, not
the fields, decides how many sets there are [infer].

Bit *i* of the coordinate-format word (`COORDFMT.SET_F16`, state-block word 17) carries set *i* at
half precision: 0.1, 1/3 and 0.7 then arrive as `0x3dccc000`, `0x3eaaa000` and `0x3f332000`, the
whole set cut to 10 mantissa bits towards zero, while with the bit clear they arrive to within
the last bit or two of the single. With two sets, bit 0 cuts set 1 and bit 1 set 2.

`OUTSEL` bits 7:0 (`OUTSEL.PLANES`) enable user clip planes. Plane 0 reads its distance from the
dword after the position: with a 5-dword vertex and bit 0, the triangle draws for +1.0 and is
removed for -1.0; with bits 1:0 and a 6-dword vertex it draws only when both distances are positive.
A plane that crosses the triangle removes it whole rather than cutting it, so a user plane acts as a
cull distance here [infer]. With a 4-dword vertex any of the bits removes the triangle or faults the
job. An `fdpc` result replaces the vertex's distance dword for an enabled plane and does nothing for
a disabled one (E095, E096). That result is held past the job: after a job whose fdpc put every
vertex outside plane N, later jobs that enable the plane and run no fdpc are removed until an fdpc
puts the vertices inside again, for planes 0, 1 and 2; while the held state is inside, the distance
dwords o4 and o5 at -1 remove nothing, for plane 0, plane 1 alone, and planes 0 and 1; plane 2's
distance dwords were not run with its state inside (E280). So a job's clip planes depend on the fdpc
of the jobs before it, which is why plane 1 alone drew in one session and was removed in another;
where the state is held, what resets it, and when the distance dwords count are open (Q039).

`OUTSEL` bit 12 puts each vertex's 1/w into the TA's object (§10.1): with it clear the object
loses its 1/w dwords and the format word bit 18, and the triangle at w 1 draws the same. Bit 13
clear changes neither the object nor the image, with zero, one and two coordinate sets (E286);
what it selects is not shown (Q069). Of the presence word's bits 16-31, set one at a time, bits
17, 18 and 22 to 25 remove the triangle, 27 hangs the job and the other nine change nothing
(E286, one run); which words they announce is open (Q069).

Evidence: E095, E096, E192, E198, E236, E237, E280, E286; Q039, Q069.

## 10. The TA's output

### 10.1 The object

The TA's object for the triangle sits at the start of the parameter buffer. It holds, in order:

1. three header words (`PB_OBJ.PDS_WORDS`): the state block's words 3 to 5, the pixel program's
   secondary pointer, size word and primary pointer, copied as given (six values set in them
   reappear unchanged, E306, one run); `0x04000004`, `0x00030001`, `0x04000000` with a position
   only, `0x04000004`, `0x00030004`, `0x0c000080` with any iterated output;
2. per vertex, its 1/w (`PB_OBJ.RHW`) followed by its iterated outputs, undivided: 1 dword a
   vertex with a position only, 3 with one 2-component set, 2 with the vertex colour (one packed
   ARGB8888 dword), 3 with a 4-dword set at half precision (16-bit pairs);
3. ISP word 0 and ISP word 1 (`PB_OBJ.ISP_WORDS`), exactly as the state block gives them (eleven
   values tried, among them the stencil reference, the pass types, the visibility test and the
   polygon offset);
4. the primitive list (`PB_OBJ.PRIM_LIST`): one 16-bit entry per primitive, two to a dword with
   the first in the low half and the last repeated for an odd count; an entry is three 5-bit
   vertex numbers from bit 0, the object's vertices numbered from 16. A triangle is (16, 17, 18)
   (`0x4a30`), a line (16, 17, 17), each point repeats its vertex [infer: the pattern of these
   dumps]. Bit 15 of an entry is set in 11 of the 24 random triangles of E307 (`0xca30`), exactly
   those of one winding, and in both entries of the first dword with `VDM_INDEX2` at `0x0f000000`
   (`0xd693ca30` for `0x56934a30`, the packed vertices differing too, E300): a winding mark fits
   [infer: one table of triangles] (E308, Q042);
5. the line width in both bytes of one dword (`PB_OBJ.LINE_WIDTHS`): ISP word 1 bits 15:8
   (`ISP1.LINE_WIDTH`, in sixteenths of a pixel, §11.12), `0x1010` at width `0x10`;
6. a format word (`PB_OBJ.FORMAT`) whose bits 7:0 are the dwords a vertex takes as stored (1, 2,
   3 or 5 in every object dumped, E308; the 45 objects dumped after the layout was written all
   have `0x00040101`) and bits 15:8 as iterated (`0x00040101` position only,
   `0x00040303` one 2-component set, `0x00040503` a 4-dword set at half precision; bit 18 is
   set while `OUTSEL` bit 12 puts the 1/w in the object (§9.4), and the vertex colour also sets
   bit 19);
7. four masks (`PB_OBJ.SET_MASKS`) with bit *i* for coordinate set *i* counted from 1; their bits
   follow the half-precision and coordinate-size settings: half precision sets mask 1, coordinate
   size 1 mask 2, size 3 mask 3, size 4 mask 4 and size 5 masks 3 and 4, which read as "half
   precision, one component, has z, has w" [infer: one value per setting, read from the dumps
   this layout was written from] (E308, Q070);
8. the packed vertices, 8 dwords for 3 vertices; a viewport z change moves three of them.

Lines and points are told apart from triangles by ISP word 0 (`ISP0.OBJ_TYPE`): a line adds
`0x8000`, points `0x18000`.

Each TA kick, and each object of a kick, writes an object of its own: in a scene over two kicks the
second's object starts a new parameter page (0x3000), a third kick's follows the first's in its
page (0x105c), as does a second object of one kick, whose third PDS word differs (0x04000070)
(E288).

The fields are placed from the stream (`CSTREAM.OBJ_ISP_ADDR` gives the ISP words, the
primitive word the vertices, the object word the primitives). This layout decodes the 28 object
dumps it was written from and the 45 taken since, all of the one format `0x00040101` (one dword
a vertex) and differing in their vertex counts (E308; pbdump.py object_fields): the new dumps
test the placement by the stream and the vertex count, not the other formats or the masks.

Evidence: E176, E178, E181, E286, E288, E306, E308; Q070.

### 10.2 Region headers and control streams

The TA data holds one region header (three dwords) per region, a 32 x 16 tile, of every macrotile
the target needs, the regions past the target's edge included: 64 headers up to 128 x 128, 128 for
64 x 192 and 256 x 256. Word 0 (`REGION_HDR.POS`) places the region, bits 23:16 stepping by 2 per
column and bits 15:0 by 2 per row, with bits 15:12 the macrotile number; its flags in bits 31:24
(`REGION_HDR.FLAGS`) mark a region outside the target (bit 25), the first and last header of a
macrotile holding target regions (bits 26 and 28), a region inside the target with no stream (bit
27) and the scene's last region (bit 31); with `CR_TE_PSG` bit 21 every target region's header
also has bit 29 (E305, one run). Word 1 (`REGION_HDR.STREAM`) is the region's stream
block, a multiple of `0x80`, or 0; word 2 is 0.

For each region it bins the object into, the TA writes a control-stream block, 128 bytes apart: a
primitive word, an object word, a third dword in some cases (more than six vertices, two lines),
then `0xc0000000` filler up to 8 dwords.

- The object word (`CSTREAM.OBJ_ISP_ADDR`) holds in its low bits the dword address of the object's
  ISP words (`0x406` for one triangle, `0xc06` and `0x41d` for the second and third kick's), and in
  bits 31:26 twice the primitives less one (`CSTREAM.OBJ_PRIMS`: 1, 3 and 9 for one, two and five
  triangles). A region's stream holds one primitive and object word pair per object that touches
  it, in the order the objects were written (E288).
- The primitive word's bits 30:29 are 2 for triangles and lines and 3 for points
  (`CSTREAM.PRIM_POINTS`); bits 28:25 are the object's vertices less one
  (`CSTREAM.PRIM_VERTICES`).
- The primitive word's bits 23:16 (`CSTREAM.PRIM_TILES`) say which of the region's two 16 x 16
  tiles the triangle meets: `0x80` the left only, `0x98` the right only, `0x90` both; bit 23 is
  set in every word seen. With `0x90` the region takes all the object's primitives (bits 15:0
  `0xffff`); with one tile bits 15:0 carry masks, and the five-copy scene adds the forms `0x8a`
  and `0x8c` with the primitive mask in a further dword. A bounding box and edge test against the
  16 x 16 tiles reproduces all 472 regions of 26 shifted triangles it was fitted to, and predicts
  all 265 regions and forms of 24 fresh random triangles on 128 x 128, 20 of them reaching past
  the target (E307, one run; ta_words.py regions). The fresh triangles confirm the generic
  overlap test, off the target too, but not the fitted boundary rules (half-open between the two
  tiles, the corners closed): no vertex or edge of theirs lands on a tile boundary, so a plain
  overlap test, closed or open, gives the same tiles, and only the forms `0x80`, `0x90` and `0x98`
  occur. The boundary rules rest on the fitted shifts alone (E180). Lines and points are not
  tested (Q070).

The region test is wider than the pixels: on 128 x 128 the triangle gets 19 streams with a pixel
centre in 17 regions, on 256 x 256 56 against 46. A culled triangle leaves no stream and every
header empty. That the ISP walks these headers is a reading [infer].

Evidence: E177, E178, E180, E181, E185, E288, E305, E307; Q070.

## 11. ISP state

### 11.1 ISP word 0

- Bits 7:0 are the stencil reference, and bit 8 is set with ISP word 2 (stencil) present in every
  probe; that it announces the word is not probed apart [infer] (§11.3).
- Bit 11 turns on two-sided stencil (§11.3).
- `ISP0.PASS_TYPE` (bits 27:25): types 1, 2, 4, 5 and 6 draw a single triangle exactly as type 0
  (opaque) does, and 3 and 7 remove it. Type 1 is a translucent pass (§11.11), types 4 and 5
  punch-through passes (§11.10).
- Bits 24:22 are the depth compare (`ISP0.DCMP_MODE`): 0 never, 1 less, 4 greater, 7 always,
  the object's depth on the left; no probed depth equals another, so 2 draws as 0, 3 as 1, 5 as 7
  and 6 as 4, and reading them as equal, less or equal, not equal and greater or equal follows
  the stencil compare's order (§11.3) [infer].
  Bit 20 (`ISP0.DWRITE_DISABLE`) stops the object writing depth; bit 21
  (`ISP0.TAGWRITE_DISABLE`) stops it writing colour while it still writes depth (E282).
- Bit 18 hangs or faults the job. Bit 28 adds samples to a single-sampled object's coverage
  (§11.8). Bits 9, 10, 12 to 14, 19 and 29 to 31 changed nothing in the probes that set them, one
  run; what bit 9 (`ISP0.BIT9`) selects is not shown, and clearing it moves nothing in the block
  [infer] (E282).

Evidence: E065, E214, E216, E224, E228, E282.

### 11.2 ISP word 1

- Bit 3 (`ISP1.VISTEST`) makes the object count its pixels into a visibility counter named by bits
  2:0 (`ISP1.VISREG`): 0 counts into `CR_ISP_VISIBILITY_COUNT0`, 7 into `_COUNT7`; with bit 3 clear
  nothing counts (E070).
- Bit 23 (`ISP1.POLY_OFFSET`) enables the polygon offset: `CR_ISP_POLY_OFFSET_UNITS` is the offset
  in ulps of the stored depth and `CR_ISP_POLY_OFFSET_CLAMP` caps it (0 no cap); the factor
  register at 4.0 adds nothing to a flat triangle (E071).
- Bits 31:26 hold a value the ISP compares with `CR_ISP_CTL` bits 5:0. Any of `CR_ISP_CTL` bits
  5:0 set removes objects of pass types 0 and 1 and leaves types 2, 4, 5 and 6 drawn. Over the 49
  pairs of seven values of each, an opaque object is drawn exactly when its bits 31:26 are at least
  `CR_ISP_CTL` bits 5:0; types 2, 4, 5 and 6 draw whatever the two hold. Our objects leave both
  at 0.

Evidence: E070, E071, E232, E233, E235.

### 11.3 Stencil

With ISP word 2 present (ISP word 0 bit 8), the stencil test compares the reference of ISP word 0
bits 7:0 with the stencil, both masked by bits 15:8 (`ISP2.SCMP_MASK`), under the relation of bits
27:25 (`ISP2.SCMP_MODE`): 0 never, 1 less, 2 equal, 3 less or equal, 4 greater, 5 not equal, 6
greater or equal, 7 always, the reference on the left. The stencil a tile starts with is
`CR_ISP_BGOBJVALS.STENCIL` (`0x04bc` bits 7:0), used only while `CR_ISP_BGOBJVALS` bit 8 is set; the
job's value acts as 0. Three operations act on the stencil: bits 24:22 (`ISP2.SOP1`) when the
stencil test fails, 21:19 (`ISP2.SOP2`) when it passes and the depth test fails, 18:16 (`ISP2.SOP3`)
when both pass; each is 0 keep, 1 zero, 2 replace with the reference, 3 increment clamped at 0xff, 4
decrement clamped at 0, 5 invert, 6 increment wrapping, 7 decrement wrapping, and writes only the
bits of bits 7:0 (`ISP2.SW_MASK`). Bits 31:28 change nothing. A second object reads the stencil the
first wrote in the same render (E284, one run). `CR_ISP_REG_04E8` at 0, 1, `0x100` and `0x101`
changes no stencil outcome (E216, E285).

With ISP word 0 bit 11 set, a back-facing triangle is decided by the stencil word of state-block
presence bit 5 and needs the back ISP word 0 of presence bit 3; presence bit 4 (a back ISP word 1)
is optional, and the back word 0's own word-2-present bit is not needed. A front-facing triangle
keeps the front words. Without bit 11 no back-face case draws.

Evidence: E216, E228, E284, E285.

### 11.4 Depth

§9.1 gives the depth (vp4 + vp5 z), its clipping and the exact compare, and §11.1 the compare and
write bits. A shader's `depthf` src0 replaces the pixel's depth at the end of a punch-through phase
(§11.10). With a depth that slopes across the triangle, `CR_ISP_POLY_OFFSET_FACTOR` at 4.0
moves the depth test's boundary as far as `CR_ISP_POLY_OFFSET_UNITS` at 0x100000 does, and at
64.0 pushes the whole triangle behind the clear depth: the factor scales the offset by the slope
[infer: two values] (E291).

Evidence: E287, E291.

### 11.5 The ZLS control word

Bit 0 of `CR_ISP_ZLSCTL`, and the value `0xffffffff`, let the triangle job complete with no pixel
written; the other 31 single bits change nothing in a job without depth or stencil buffers. Render
flag `0x10` reaches the same bit: the 3D kick and the partial render's restart OR 1 into the
register when it is set, and the job then completes with no pixel.

The 3D kick adjusts the word from render flags `0x80` (`DEPTH_BUFFER`) and `0x100`
(`STENCIL_BUFFER`) and the RT status word's bit 1 (§6.4). With that bit clear: if the flags have
no bit outside `0x180` the word is kept; otherwise a clear `0x80` removes bits `0x44000`, a clear
`0x100` removes `0x22000`, and with neither flag set bits 2:1 go too. With the bit set, `0x80` adds
`0xc000` and `0x100` adds `0x2000`. How the ISP uses these bits is not shown. The closed driver's
values for a depth-buffered render are `0x0017100c` for a window surface's first render and
`0x0017700e` for every later one (bits 1, 13 and 14 added), `0x0017300e` under
`ExternalZBufferMode=2` and `0x00140008` for a texture's depth attachment (E335-E337).

The control's fields, from the stores and loads of E411 and E465 to E467 (the library's jobs, a
depth buffer and, where noted, a stencil buffer):

| bits | meaning |
|---|---|
| 0 | the job completes with no pixel (E057) |
| 1 | the load is on; bits 13 and 14 act only with it (E467) |
| 2 | the stores are on at all (E411, E466) |
| 11:3 (G) | the tile pitch minus one: a tile row starts G + 1 tiles on (§11.6; E465) |
| 13 | with bit 1: load the stencil (E467) |
| 14 | with bit 1: load the depth; the sign bit of a loaded depth is cleared (E467) |
| 17, 18 | store the stencil (E411), store the depth (E411, E466) |
| 19 | store the float depth negated (E466) |
| 26:24 | stored depth format: 0 float32, 1 24-bit, 2 16-bit, 3 to 7 packed or none (E466) |
| 12, 15, 16, 20 to 23, 27 to 31 | change nothing seen (E411; Q071) |

The earlier reading of bits 5 to 11 as faulting and of bits 3 and 4 as a region is [infer] the pitch
field G running past the 16 pages of the scratch buffer of E411: E465 recomputes E411's pages for
bit 3 cleared, bit 4 set and bit 26 by hand and they match; no fault was reproduced.

Evidence: E057, E163, E169, E335-E337, E411, E465-E467; Q071, Q088, Q101.

### 11.6 Load and store bases

With `DEPTH_BUFFER` set, the depth store (4096 floats of a 64 x 64 target) lands where
`CR_ISP_ZSTORE_BASE` (`0x0488`) points and never at `CR_ISP_ZLOAD_BASE` (`0x0484`), and the depth
load reads from `CR_ISP_ZLOAD_BASE` whatever `CR_ISP_ZSTORE_BASE` holds. The stencil store lands
where `CR_ISP_STENCIL_STORE_BASE` (`0x0490`) points only when its bit 31 is set and the stencil
flag is on, never at `CR_ISP_STENCIL_LOAD_BASE` (`0x048c`). For a render-target index *i* > 0 the
3D kick adds *i* times the render details' strides to these bases (§5.2). With a depth buffer of
the target's size the store of the clearing control `0x0017100c` writes only a window of it: 64512
dwords at 1024 x 768 and 326656 at 4096 x 4096 in every job (62122 x 1.0 and 2390 x 0.5 for the
triangle at z 0.5 at 1024 x 768 with the whole scene in the buffer); the load-only control
`0x0011700a` stores nothing in such a job (E461, two runs of each 1024 x 768 case).

The window is the address arithmetic of the store (E465). The target is cut into 32 x 16 pixel
tiles; tile (*tx*, *ty*) is stored at dword 512 * (*ty* * (G + 1) + *tx*) of the buffer, G being
`CR_ISP_ZLSCTL` bits 11:3 (0x0017100c has G = 1, a pitch of two tiles), and inside the tile the
dword index has the bits y0 x0 y1 x1 y2 x2 y3 x3 x4 from the lowest (x and y the pixel's offsets
in the tile, 32 x 16 pixels, 512 dwords for the 32-bit formats). With a pitch smaller than the
tiles of a row the tiles overlap and the last one written keeps its dwords, so the window of a
target of *tw* x *th* tiles is (*th* - 1) * (G + 1) + *tw* tiles of 512 dwords: 126 tiles at
1024 x 768 (48 rows of 32) and 638 at 4096 x 4096 (256 rows of 128) with G = 1, which is where 64512
and 326656 come from. With G + 1 at least *tw* no tiles overlap; the library's jobs, which leave G
at 1, have therefore never stored a whole buffer of a target wider than 64 pixels. The 16-bit
format has 256 dwords a tile at the same pitch, in the order x0 y1 x1 y2 x2 y3 x3 x4 from the
lowest bit of the dword index, y0 choosing the half of the dword, the even row in bits 15:0
(E466). In 18 cases on 13 target sizes (one run each) every stored dword is at the rule's address
in 16, among them sizes that are not multiples of the tile (1000 x 600, 258 x 130, 34 x 18,
1536 x 1010) and G from 0 to 511; the two overflowed 4096 x 4096 jobs have 80640 and 48000 stored
dwords not at the rule's address (zeros [infer], E468). Each case ran once, the address rule was
checked by the dataset's script at run time and the stored data holds no raw dumps to recompute it
from (E465).

Evidence: E058, E163, E461, E465, E466.

### 11.7 Multisampling

`CR_ISP_MULTISAMPLECTL` (`0x04c8`, `0x88` in our jobs) places the single-sampled pixel's sample:
10 of the 256 values of its byte 0 leave the triangle as it is, the others move its edges, 8 being
the centre of each nibble's stair (E064).

`CR_ISP_MSAA` (`0x042c`) bits 1:0 (`CR_ISP_MSAA.MODE`) choose how many samples a pixel stores and
how: 0 one, byte 0 of `CR_ISP_MULTISAMPLECTL`; 1 two, stored side by side in x (target pixel
2x + i holds sample i of pixel x); 2 four, stored as a 2x2 block (sample i + 2j at (2x + i, 2y +
j)); 3 hangs the job in every setting tried (E210). The samples are bytes 0 to 3 of
`CR_ISP_MULTISAMPLECTL` in order, each x in bits 3:0 and y in bits 7:4; the MTE's position word
and `CR_ISP_SAMPLE_POS` do not place them. The sample-layout fitter (`isp_words.py layout
--joint`) fits these layouts with no pixel missed over eight positions of a known edge inside the
target's first 16x16 tile; on the library triangle the stored images are cut to whole tiles and
shifted, and the tiles past the first land at their own place plus a constant, in the first and
third tile columns with the TE anti-aliasing bits clear and in the middle one with them set (E415,
Q030) (E281).

Bit 31 (`CR_ISP_MSAA.ENABLE`) clear stores none of the triangle in modes 1 and 2, while the
parameter buffer and TA data are byte for byte those of the bit set: it acts after tiling. The TE
anti-aliasing bits (`CR_TE_AA` 31:29) remove the triangle when bit 31 or 30 is set without bit 29
and change nothing with bit 29 alone; what each selects beyond the tile columns is open (Q030)
(E281).

Evidence: E064, E074, E210, E211, E219, E220, E281, E415; Q030.

### 11.8 Sample positions and ISP word 0 bit 28

With ISP word 0 bit 28 set, `CR_ISP_SAMPLE_POS` (`0x0520`) widens a single-sampled object's
coverage: 55 values give six images, none losing a pixel. Byte *k* places sample *k* at (bits 3:0,
bits 7:4) / 16 of a pixel from its top-left corner. At the default `CR_ISP_MULTISAMPLECTL` two rules
reproduce all 55 images: a pixel is covered when any of eight samples is inside the triangle, the
four bytes of `CR_ISP_MULTISAMPLECTL` and the four of `CR_ISP_SAMPLE_POS`; or when one of the four
samples of `CR_ISP_SAMPLE_POS` or the pixel centre is inside, the centre counted inside on every
edge (without that tie rule the centre fits 53 of the 55). The coverage-sample probes part the two:
with both words at `0xcccccccc` or `0xeeeeeeee` every one of the eight samples lies past the long
edge, and the 36 pixels along it are lost, as the eight-sample rule says and the centre rule does
not. The eight-sample rule, under the top-left rule (a sample on an edge is inside only on an edge
that runs up the screen; of it only the long edge's exclusion is seen), predicts all 56 images of 28
settings, each run twice, pixel for pixel, and the centre rule misses 12, 24 or 36 pixels in 10 of
the 28 settings (20 of the 56 images). A centre sample under the top-left rule, added to the eight,
also fits; the centre counted inside on every edge does not. Each byte of both words is x in bits
3:0 and y in bits 7:4. With bit 28 clear only byte 0 of `CR_ISP_MULTISAMPLECTL` samples (E278, one
run). Under 4x multisampling, three values of `CR_ISP_SAMPLE_POS` give one image, and bit 28 hangs
the job, which is open (Q031).

Pointed at a scratch buffer, `CR_ISP_SAMPLE_POS` changes no scratch dword under any ISP word bit
tried: it is not the base of a table the ISP reads or writes there.

Evidence: E214, E215, E224, E278; Q031.

### 11.9 Render-constant ISP registers

`CR_ISP_LINE_SAMPLE_POS` (`0x0418`), `CR_ISP_REG_04DC`, `CR_ISP_REG_04E8`, `CR_ISP_SAMPLE_POS` and
`CR_REG_0800` change no pixel of a copy, a fill or a textured triangle at any implemented bit, 0 or
`0xffffffff`; with 42 overlapping opaque triangles the covered-pixel count does not move. 0x0418
is read by lines only (§11.12), 0x0520 by ISP word 0 bit 28 (§11.8). `CR_ISP_REG_04E8` at 0, 1,
`0x100` and `0x101` changes no stencil test and no pixel or visibility count of 42 overlapping
copies, depth always or less (E285). `CR_ISP_REG_04DC` bit 1 hangs every punch-through pass tried,
whatever the shader's ending (fb, nfb, `depthf`, `nop.end`), while 0, 1 and 4 give the pass's own
image; on opaque and translucent passes of five copies with depth less it changes neither the kept
copy nor the visibility count (E290), so the punch-through pass alone stops (Q072). Bits 5:0 of
`CR_REG_0800` (48 outside a render) do not limit pixel tasks: none of eight values from 0 to 63
changes a long shader's render time.

Evidence: E067, E068, E072, E073, E213, E222, E225, E285, E290; Q072.

### 11.10 Punch-through

In a punch-through pass (`ISP0.PASS_TYPE` 4) of five overlapping copies, depth test less, a pixel
is kept only when the pt phase ends in `atst8` with the feedback mode fb, a passing alpha test and
a control word (src1) with bits 0 and 14 set: `0xe001`
keeps the nearest copy (1062 pixels of depth 0, 36 of the next). Bit 2 or bit 3 makes the last copy
win, as if the depth test were always; the other bits change nothing.
nfb and `nop.end` keep nothing. optdwd and the twosided flag keep the same pixels as fb, on front
and on back faces, and with ISP word 0 bit 20 set; if bit 20 is the depth-write-off bit, the
feedback's depth does not follow it [infer] (E226, E227).

The kept pixels' depth is the same without `pcoeff`, without the source-34 iteration and without
both; it moves between runs only when `pcoeff` runs without the iteration it reads. What `pcoeff`
hands the ISP is open (Q032). An `atst8` straight after `pcoeff` drops the object, and one `nop`
between them lets it draw. `depthf`'s src0 replaces the pixel's depth in the depth test, in pass
types 4 and 5: 1.0 draws nothing and 0.5 - z makes the last copies win.

A punch-through pass neither tests nor writes the ISP stencil: no stencil compare, no bit of the
control word, no render-level ISP word or `CR_ISP_REG_04DC`/`CR_ISP_REG_04E8` bit tried makes it
obey the stencil, and a second object testing for the stencil it would have written finds none.

Evidence: E082, E083, E217, E218, E226, E227, E229, E230, E231, E234, E244; Q032.

### 11.11 The translucent pass

In a translucent pass (`ISP0.PASS_TYPE` 1) a pixel shader's `o0` holds the pixel's current colour
when it starts, at every pixel of the triangle (E077), and the stored pixel is exactly the
shader's `o0`: a constant written without reading `o0` is stored as it is, `o0` passed on leaves the
background, and `o0 | 0xff` stores the background with its low byte set. In the one ISP and PBE
state run, with no blend-related word varied, no unit after the shader blends: blending is the
shader combining its colour with `o0` [infer] (E283). In the opaque pass `o0`
starts as a leftover: on 390 to 450 of the triangle's 1062 pixels at 64x64 it holds an earlier job's
colour, the rest the background, with counts that repeat (E417, Q073).

Evidence: E077, E283, E417; Q073.

### 11.12 Lines and empty regions

A line (index list type 1, ISP word 0 object type 1) takes its span sample where
`CR_ISP_LINE_SAMPLE_POS` bit 0 says: a column x is covered when x + 1/2 (bit 0 at 1) or x + 1 (at
0) lies in the line's span [start, end). At both values the column's rows are those whose centre
r + 1/2 lies within half the width of the line's y at x + 1/2, the upper one on a tie: bit 0
moves the span's sample, or shifts the span by half a pixel, and nothing shows a sample at y + 1.
This model fits all 32 cases of two runs, six of eight cases moved in x and y together (the 3/4
cases miss 2 pixels) and all nine widths with no pixel missed [infer: one x-major line]. Moving
the line by sixteenths moves its end columns at 8 + 8/16 (bit 0 at 1) and 8 + 1/16 (at 0);
triangles draw the same at both values (E279). It is not a depth-bias format: the
polygon offset of a sloped depth is the same at 0 and 1 (E291). `ISP1.LINE_WIDTH` is the width in
sixteenths of a pixel across the minor axis: an x-major line of 48 columns covers 48 x width / 16
pixels from 0x04 to 0x80, and nothing at 0 (E279, one run).

`CR_ISP_CTL` bit 8 (`CR_ISP_CTL.PROCESS_EMPTY_TILES`, set in the library's jobs) makes the 3D render
the 32 x 16 regions the TA left without a control stream. Clear, it skips them and leaves their
pixels as the target held them, every such region but the scene's last: 1 region at 96 x 64, 12 at
128 x 128, 33 at 256 x 128 and none at 64 x 64. Bits 24 and 19:16 change no pixel at any of these
sizes (E289, one run).

Evidence: E279, E289, E291.

## 12. Pixel side

### 12.1 The pixel-event program

The render's pixel-event program runs per tile. On a render larger than 32 x 16 its input `ir0`
reads `tile_y << 10 | tile_x` in 16 x 16 tiles (59 of the 60 tiles that stored anything on a 128 x
128 render), on a 32 x 16 render 0; `ir1` reads 2, or 6 on the last tiles (pds_isa.md §8.12). The
end-of-tile emit's sideband needs bit 9: clear, it hangs the job, also on a 32 x 16 target, a single
32 x 16 tile. A second emit in the same tile leaves the next job's image wrong, which reads as that
emit being carried out during the next job [infer]. So bit 9 marks an emit that counts against a PBE
tile [infer] (Q074), not tile-relative addressing. Pack mode 3 stores RGB565 (E030).

The program chooses the task from data dword 8 (`ds0[4]`, 0x100 in our program): it runs the
end-of-tile task only where `~ir1 & dword 8` is not zero. At 0 or 0x2 no tile is emitted and the
job writes no pixel; at 0x4 the last tiles, those with `ir1` bit 2, are skipped (the bottom-right
32 x 16 pixels); a value with any bit `ir1` never has leaves the image as built, in the fill, the
copy and the triangle alike (E265).

Evidence: E030, E130, E239, E240, E265; Q074.

### 12.2 Iteration and texture

A primary pixel program's `douti` delivers nothing to `pa0` unless the task waits for a texture
fetch (`DOUTU1` `0x02000004`) and the program issues the fetch's `doutt`. Then source 0 is the
pixel's x + 0.5, source 1 the coordinate set's x, sources 32 and 33 `0xff000000`, sources 2 to 31,
34 and 35 zero, and 36 to 63 leave the texel. `DOUTI0` bits 23:22 are the components less one (0 to
2 exact; 3: the texel is in pa4 and pa3 is 1.0, E420; Q021), bit 21 takes the first vertex's value,
bit 28 writes a half float. With the colour output select and coordinate-size words, source 32 gives
the vertex colour as ARGB8888, that of the vertex the shade model picks on 723 to 753 of the 1062
pixels. Source 0 with two components (`DOUTI0` `0x20400000`, the completion bit set, under `DOUTU1`
bit 24) is the pixel's position: x + 0.5 in `pa0` and y + 0.5 in `pa1` at 1062 of 1062 pixels, three
runs each (E437), which a program that has no vertex coordinate set, a background object's, can use
as its place. With a colour iterated into the attributes and a fetch, the fetch wait alone delivers
colour and texel; bit 24 set or clear changes neither, and bit 24 without the completion bit hangs
(E436). A coordinate set after the vertex colour is read from vertex dwords that exist: with the
colour select word at the vertex's size (`OUTSEL.VTX_SIZE` 10, 11 or 12 for 6, 7 or 8 coordinate
dwords, word 13 = `0xa3800`, `0xb3800`, `0xc3800`) source 1 reads varying non-zero values, with the
size left at 8 over a longer vertex and the default coordinate-size word it reads 0 in every pixel
(the triangle then has 856 pixels), and a coordinate-size word of 2 or 0x12 on 6 coordinate dwords,
or 3 on 7, faults the job, with the size field matching or left at 8 (E459). With the set
delivering, bit 24 set or clear still changes neither registers nor image under the fetch wait (33
of 33 completed jobs with both bits, 36 of 36 with bit 25 alone, E460); a job with both bits hung in
3 of 36 there (each in the probe that reads the last register the program iterates) and in 1 of 30
in E454, none of 60 more with both bits on the colour, 4 of 126 jobs with both bits in all, and none
of 96 with bit 25 alone (Q093).

A power-of-two 2D texture (`TEXTYPE` 0) is twiddled: texel (tx, ty) is dword *i* with ty's bits in
the even bits of *i*; RGBA8888 holds R in byte 0. T3 bits 26:23 do not change what one fetch writes;
with two fetches, the second texel lands in the primary attribute the first fetch's field names
(values 0 to 4 and 6).

Evidence: E035, E131, E132, E133, E242, E420, E436, E437; Q021.

The field reaches 15: at 8 and 15 the second texel is in pa8 and pa15, as f32 channels too
(E277). On a twiddled mip chain T0 bits 20:17 (`T0.MAX_LEVEL`) cap the level read, 0 and 15
reading level 0 only, and bits 26:21 bias the LOD by (value - 63) / 8 before the nearest level
is taken: level = max(0, min(round_half_up(LOD + bias), maximum)) gives all 192 reads at four
LODs on a five-level chain, a biased LOD below 0 reading level 0 (E276). On a 128x128 chain of
eight levels the same model holds with the level capped at the last (a maximum of 8 to 14 at LOD 8
and 9 reads level 7), 15 reads level 0 at every LOD like 0 (so it is no beyond-the-chain fallback,
and reads as a no-mipmap value [infer]), the bias fits 128 of 128 reads, and with T0 bit 9
(`T0.MIPFILTER`) set the result is the channel-wise linear blend of the texels of the level
floor(LOD + bias) and the next by the fraction (15 of 15 cases, byte for byte, three runs each,
E441). Bit 18 is not a mipmap disable. In a copy (one strided texture, point sampling) T3 bits
7:0 offset the texel read, x in 7:4 and y in 3:0, by a signed 4-bit count, clamped at the edge;
bits 18 and 19 scale the coordinates by 2 and 4, bits 27 and 28 read half- and quarter-size
images packed after the source, and T3 bits 10 and 14 and T0 bit 27 change the read in ways not
decoded (E274; Q078).

Evidence: E274, E276, E277, E441; Q078.

### 12.3 The end-of-tile emit and the pixel back end

The end-of-tile program hands the PBE four words and a sideband (asm/transfer/use_eot.s):
`emitpix1` takes EMIT0 and EMIT1, `emitpix2` EMIT2, EMIT3 and the sideband as an immediate, which
carries bits 13:0 only. Varying each in the triangle's end-of-tile program (E266, E267):

| word | bits | what the PBE does with them |
|---|---|---|
| EMIT0 | 12:0, 28:16 | the store rectangle's minimum x and y |
| EMIT1 | 12:0, 28:16 | its maximum x and y, inclusive |
| EMIT0, EMIT1 | 15:13, 31:29 | nothing seen, but EMIT1 bit 31: it hangs the job |
| EMIT2 | 15:8 | four-pixel units stored of each 32 x 16 tile: 0x80 all, even v 4v pixels |
| EMIT2 | 27:16 | the row pitch, (value + 1) x 8 bytes |
| EMIT2 | 6:0 | fit by an offset into the order the tile's pixels are read in (x0, y0, x1, x2, x3, y1, y2 of a 16 x 8 block) [infer] |
| EMIT2 | 7 | nothing seen |
| EMIT2 | 29:28 | the image rotated by 90, 180 or 270 degrees (1, 2, 3) |
| EMIT2 | 30 | each tile's 2x2 box average in its top-left 16 x 8 pixels [infer] |
| EMIT2 | 31 | the image scaled by two, (X, Y) from (X/2, Y/2), after the rotation |
| EMIT3 | 31:2 | the address of pixel (0, 0); bits 1:0 ignored |

In the count, 0 stores no pixel, an odd value hangs the job and a value above 0x80 lands extra
units over the tile, with values that change from run to run. Clipped pixels hold the image's
values where stored and the target's elsewhere: the rectangle
bounds what the PBE stores, not what the tile computes [infer]. A count below 0x80 stores the
units from the first rows of the tile's two halves of eight rows (rows 0 and 8 first). Bits 28,
29 and 30 fit every pixel of their images in both runs; the triangle is symmetric about x = y,
so bit 28's image is also a rotation by 90 degrees and bit 29's an anti-transpose, readings an
image without that symmetry would tell apart (E267). With a shader that names each pixel
(E382) every pixel of bits 29:28 at 1, 2 and 3 lands rotated by 90, 180 and 270 degrees over the
whole target, so bit 28 is a rotation, not a mirror; bit 31 stores (X, Y) from (X/2, Y/2); bits
6:0 at 1, 2, 4, 8 and 16 fit a read of the pixel that many places on in a tile's order [infer]
(928 to 1053 of about 1050 pixels; a carry out of a 16 x 8 block lands elsewhere). Two emits per
tile hang a job of several tiles; on one tile they complete and the later jobs store a tile or none
by turns until a reset (E386).

The sideband (E030, E031, E239, E269): bits 5:0 the pack mode; bits 8:6 the channel a one-channel
mode stores (mode 8: 0 alpha, 1 red, 2 green, 3 to 7 blue; mode 7: 0 alpha and red, 1 to 7
green and blue; modes 15, 18, 24, 25 and 28 ignore it, E383), no effect seen in modes that store
several channels, under multisampling or on several tiles; bit 9 needed to complete a tile
(§12.1); bit 10 dithers the modes that drop colour bits (RGB565, ARGB1555, ARGB4444), moving
pixels one step of one or two channels by their value and their place in a 4 x 4 cell of x
and y, an ordered dither [infer] (one run); bit 11 faults the job;
bit 12 stores fixed words of no colour (zeros in modes 7 and 8); bit 13 rearranges the pixels
(E030). Pack modes 22 and 34
read `o0` as an IEEE single, its sign, NaN and exponent, at most of the triangle's pixels,
and store the rest from somewhere the shader did not write (E270); mode 34 stores bits 30:20 of
a single in bits 21:11, and with `o0`-`o3` written each mode shows `o0` at some pixels and
other output registers at others, the pixel task having one output dword (E387). That depends on
the pixel task's setup: with `ISP0` bit 26 or 27 set, `CR_REG_0148` bit 0 set and the state
block's word 4 at `0x00030001` (one data row) `o1` to `o3` stop landing on other pixels (room for
four output dwords is the reading [infer]) and the pack modes show one value a pixel (E406;
Q012). Under it mode 22 puts `o0` in bits 31:30 and `o1` in bits 19:10, placed by saturated
values only [infer], and mode 34 stores `o1`'s bits 30:20 in bits 21:11 at the triangle's pixels,
shown on a mid-range ramp.

`CR_REG_0400` bit 25 inverts the stored alpha channel wherever the pack mode puts it: bits 31:24
in ARGB8888 and ABGR8888, bits 7:0 in BGRA8888, nothing in RGB565; bits 11:0 change no pixel in
pack modes 0 to 3 (E268). Bits 7:0 are the threshold of ARGB1555's one-bit alpha: set above the
low byte, clear below it; bits 11:8 change nothing; bit 25 inverts the alpha in modes 4 and 5,
not in mode 8 (E385; Q044).

What stays open: what the count's bit 8 and the values above 0x80 are, and where a carry of
EMIT2 bits 6:0 goes (Q040); sideband bits 11 and 12 (Q046); the formats of pack modes 22 and 34
(Q012); `CR_REG_0400`'s threshold at an equal alpha (Q044); the state a double emit leaves (Q074).

Evidence: E030, E031, E239, E266, E267, E268, E269, E270, E382, E383, E385, E386, E387, E406; Q012,
Q040, Q044, Q046, Q074.

## 13. HWPerf

The HWPerf routine (from `0x1979`) appends a 100-byte record after a header holding `CR_TIMER`:
`CR_HWPERF_COUNTER0` to `8` (`0x0044`-`0x0064`), then `0x0e84`, `0x0e88`, `0x0e8c`, `0x0e90`,
`0x0eb8`, `0x0eb4`, `0x0ebc` and `0x0ec0`, whatever the record type; each of its 33 callers first
tests a bit of the HWPerf status word. The kernel command SET_HWPERF_STATUS writes `0xffffffff` to
the buffer's dword 2 and stores its data dword 0 (bit 0 cleared) as the status; with bit 0 set it
writes `CR_HWPERF_CTRL` = `0x1ff` and pulses `CR_HWPERF_PULSE` (`0x0e80`, 1 then 0, its only
access); with a non-zero status it puts HostCtl's group in `CR_HWPERF_CTRL` bits 12:9. The TA kick
records type 3 with the page count, the 3D kick type 4.

The buffer's dword 0 is the write index and dword 1 the read index; records start 12 bytes in, 256
slots, and a full buffer keeps its write index. Read from a shader around 24 `fmad`s, in a run that
set no counter group, `0x0044`-`0x0064` read 0, `0x0e84`, `0x0e88` and `0x0e8c` stay the same, and
`0x0e90`, `0x0eb4`, `0x0eb8`, `0x0ebc` and `0x0ec0` rise.

With a group set (debugfs `hwperf`, status 0x11) the group selects what `0x0044`-`0x0064` count:
in group 0 `CR_HWPERF_COUNTER3` is the pixels a job shades, exactly; groups 7 and 9 to 15 count
nothing in the jobs tried. Whatever the group `0x0e84` counts renders, `0x0e88` jobs, and
`0x0e8c`, `0x0e90` and their sum `0x0eb8` rise with the TA's work, the pixel work and both
[infer: busy cycles] (E359, one run; the other counters per group are Q075).

Evidence: E149, E150, E152, E158, E163, E359; Q075.

## 14. On the hardware

A render job built by our kernel from our own programs, and submitted from userspace, draws the
first triangle exactly: every pixel as the CPU reference computes it, at 64 x 64, 128 x 96, on a
context sized for 256 x 256 and after a faulting render (E023); on 13 sizes up to sixteen rows of 32
x 16 tiles (E148); on 16 sizes up to 4096 x 4096 with the library's macrotile rule (E174). A 4096 x
4096 render takes about 18 s, a 1024 x 768 one about 0.9 s. The render node's interface to these
jobs is render_uapi.md §8.4; the PB overflow it reports is §6.4.

What the EDM leaves in the transfer path's page directories is transfer.md §4.4: there, the pixel
side translates through the client's directory and read-only aliases of the EDM's buffers suffice
(E151). For a render, the TA and 3D requestors read through list 1 on a freshly reset GPU
(CR_BIF_BANK0 reads 1 for the TA index and the 3D index during completed renders, E457); read-only
aliases of the buffers 6, 7, 8, 10 and 11 are not needed in the client directory, each left out
alone (10 of 10 runs exact), while TA3DCtl must be there and writable: left out, or read-only, the
first job faults at its page through list 1 (E457). That list 1 holds the client's directory, and
the buffers left out together, are open (Q076).

Evidence: E023, E148, E151, E174, E457; Q076.

### 14.1 The closed driver's jobs, from captures

The closed GLES1 and GLES2 stacks, run under the extraction harness on the laptop (13 capture
tables, 604 runs, 9 of them refused by the closed stack), give the state the vendor's driver
writes for each piece of GL state. Our jobs compare as follows.

- **Objects.** The render context is 0x44 bytes with flags NEW and OWN_PB; dword 2 is the page
  directory's physical address (the client registers it for patching) and dword 7 a 0x40-byte
  parameter-heap object at the page table's base + 0x40000, in both stacks (E323). The RT data
  set is 0x88 bytes: a header and two RT data used in turn, one per scene; header dword 5 counts
  them (2; ours 1), RT data dword 0 is the context, dwords 8 and 9 the tail pointer cache and its
  size (E325). The PB descriptor's default words equal ours, addresses aside: 0x422 pages, the
  thresholds 0x432, 0x400, 0x400, 0x300; PBSize 1 MiB and 8 MiB give 98 pages, 768 KiB and less
  fail at eglInitialize (E327; Q084).
- **Kicks.** A frame is a draws kick and a closing kick of its own that holds only the
  end-of-scene blocks (`FRAG_FLAGS.BIT10`, `CR_TE_PSG` bit 22); the TA status words carry the
  control stream's end offset and the kick count (E324). The TA command is 0x2a8 bytes plus 8
  per 3D patch, rounded up to 0x40; its zero-word TA registers are 0 in every kick (E328). Only
  eight TA registers and three address words move across all variations (E329).
- **Render details.** Of the 52 register words, 24 never move; each of the 28 others moves with
  one feature (E330). Ours differs from a closed one-triangle job in `CR_ISP_CTL` bit 8 and
  0x04c4 bit 25 only (E326, our job read back on the laptop). Our job needs bit 8: with it clear
  36352 of 65536 pixels at 256x256 stay unwritten; 0x04c4 bit 25 changes nothing (E408; Q099).
- **Tiling.** `tiling3d.py`'s rule holds at all 222 target sizes from 1 x 1 to 4096 x 4096;
  four macrotiles start at an area of 640 x 480; 4x multisampling departs from it (E331, Q086).
- **VDM and MTE.** Streams hold only state, index-list and terminate blocks, closing the same way
  every time (E349). Index lists are 6 words (E346; Q092, Q094). Each MTE state block is exactly
  the words its presence word announces, and `DOUTD1` is a two-dimensional copy (burst, lines,
  offset, stride) (E347). Region clip is in 32 x 16 tiles from the bottom, the viewport words GL's
  transform, the term word the last 32 x 32 block (E348).
- **PDS.** A pixel PDS pointer holds the program offset in bits 23:0 and its data rows in 31:26;
  `PDS_SIZE` bits 24:18 hold at least the secondary's constant rows (E343). USSE code-address
  words use base 0 for pixel and base 10 for vertex programs (E344). The secondary and primary
  shapes and their `DOUTU1` values are E345; bit 24 goes with an attribute the primary iterates
  into the attribute registers (E364); under the fetch wait the colour and the texel arrive
  with the bit set or clear (E436), also when the primary iterates the vertex colour (E454) and a
  coordinate set before the fetch on vertices that carry its dwords (E459, E460); 4 of 126 jobs
  with both bits hung against none of 96 with the fetch wait alone (Q093).
- **ISP.** Depth compares follow GL's function order, ISP2 is GL's stencil state, `ISP1.CMASK`
  the colour mask (E332); pass types 0, 1, 3 and 4 only (E340); polygon offset sets
  `ISP1.POLY_OFFSET` with GL's factor and units (E338); 4x multisampling moves seven registers
  (E339; Q089); lines and points carry glLineWidth x 16 (E340). The background object's data holds
  texture words describing the target as a strided texture, in every run of the two tables
  captured; that it samples them is inferred (E334).
- **ZLS.** A window's depth and stencil share one allocation; the first ZLS render carries six
  3D patches, later ones one; the ZLS control values per case are E335-E337 (Q088).
- **PBE and textures.** The end-of-tile words: `EMIT2.LINE_STRIDE` is the pitch in pixels / 2 -
  1, dither follows GL, MEMLAYOUT marks a texture target (E333). Texture words per filter, wrap,
  format and size, and YUV streams through colour-space set 0 or the USE coefficients, are E342
  and E341.
- **Programs.** Of the 46 USSE forms still open, the closed compilers use 14 (E350).

Evidence: E323-E350; Q084-Q086, Q088, Q089, Q092-Q094.
