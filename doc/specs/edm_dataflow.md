# SGX545 EDM dataflow: every structure word and register

*Generated from `firmware/edm-dataflow-3d/edm_dataflow.tsv` (resgx545-data) by
`harness/ukernel-extract/edm_dataflow.py`; do not edit.*

A complete forward dataflow analysis of the EDM microkernel (the image is `$RESGX545_UKERNEL`): our
disassembly of the firmware, for interoperability; facts only, no code. Every routine between the
label addresses is analysed, without aiming at any field: values are followed through moves,
arithmetic, loads, stores, branches (paths that disagree leave the value unknown) and calls. The
analysis starts from instruction 0, from every label no code reaches (the PDS-entered tasks and the
kernel CCB handlers) and from any code still unreached. Entry values: `sa0`, `sa1`, `sa2`, `sa22`
and `sa43` point at TA3D_CTL, HOST_CTL, CCB_CTL, the kernel CCB and the HWPerf buffer (the captured
TA3DCtl, `doc/specs/hw_spec.md` §11.1); a kernel CCB handler receives the command's words in
`r4`-`r11`, `r7` typed by the command (`doc/specs/transfer.md` §5).

Names are glossary terms (`doc/glossary.md`) or, where the glossary has none, offsets: registers
`0x0abc`, structure words `STRUCT+0xOFF`, secondary attributes `saN`. Routines and branch targets
are instruction indices (byte address / 8). Each use gives its count and up to three routines. `as &
0xffff` is the transform applied on the way; `when ...` the predicate that guards a write;
"branches" gives the condition that takes the branch, its target and, for a short forward skip, what
the other path runs. `?` is a value the analysis could not follow; such accesses are counted in §6,
not guessed.

Evidence: E013 (the dataflow record; dataset firmware-edm-dataflow-3d).
